# 1. DPO의 점수는 확률이 아니라 로그확률

DPO에서 `chosen`, `rejected`에 나타나는 음수 값은 확률이 아니라 응답 전체의 로그확률(Log Probability) 합이다.

확률은 `0~1` 사이이지만, 확률에 로그를 취하면 대부분 음수가 된다.

$$\log(0.8)\approx-0.223$$

응답 점수는 프롬프트를 제외하고 응답 토큰과 EOS 토큰의 로그확률을 합산한다.

따라서 값이 덜 음수일수록 해당 응답의 확률이 상대적으로 높다.

- `-3`은 `-10`보다 높은 점수
- `-50`은 `-200`보다 높은 점수
- 로그확률이 음수라고 해서 잘못된 값이 아님

# 2. Margin은 chosen의 절대 점수가 아니다

DPO의 Margin은 `chosen`의 점수 자체가 아니라 Policy와 Reference에서 나타나는 `chosen - rejected` 상대 점수 차이를 비교한 값이다.

$$m=\beta\left[(s_{\mathrm{policy}}^+-s_{\mathrm{policy}}^-)-(s_{\mathrm{ref}}^+-s_{\mathrm{ref}}^-)\right]$$

Margin이 양수라는 것은 다음을 의미한다.

> Policy가 Reference보다 `chosen`을 `rejected`에 비해 상대적으로 더 선호하게 되었다.

따라서 Margin이 증가했다고 해서 `chosen`의 절대 로그확률이 반드시 증가한 것은 아니다.

예를 들어 DPO 학습 후:

| 구분 | DPO 전 | DPO 후 |
|---|---:|---:|
| chosen | -0.11 | -55.72 |
| rejected | -39.31 | -227.82 |

`chosen`도 낮아졌지만 `rejected`가 훨씬 더 크게 낮아졌다.

즉,

- chosen 절대 점수: 감소
- rejected 절대 점수: 더 크게 감소
- chosen과 rejected의 상대 차이: 증가
- Margin: 증가 가능

따라서 **양수 Margin = chosen 절대 확률 상승**으로 해석하면 안 된다.

# 3. Margin과 DPO Loss 사이에는 Sigmoid가 있다

Margin이 바로 Loss가 되는 것이 아니다.

흐름은 다음과 같다.

`Margin → Sigmoid → 선호 확률 → -log → DPO Loss`

Sigmoid 함수는 다음과 같다.

$$\sigma(x)=\frac{1}{1+e^{-x}}$$

시작 시 Policy와 Reference가 같은 SFT 모델이면 두 모델의 상대 점수 차이가 같다.

따라서:

$$\mathrm{margin}=0$$

Margin을 Sigmoid에 넣으면:

$$\sigma(0)=0.5$$

DPO Loss는:

$$L=-\log(0.5)=\ln2\approx0.693$$

여기서 `0.5`는 chosen 응답 자체의 생성 확률이 아니다.

> DPO 목적함수 관점에서 chosen이 rejected보다 선호될 확률이 0.5인 상태이다.

# 4. DPO Loss가 작아지는 방향

헷갈렸던 부분은 `margin`이 0에 가까워질수록 Loss가 작아진다고 생각한 것이다.

DPO Loss는 다음과 같다.

$$L=-\log\sigma(\mathrm{margin})$$

Margin이 커질수록:

`Margin 증가 → Sigmoid 증가 → 1에 가까워짐 → DPO Loss 감소`

따라서 DPO는 기본적으로 **Margin을 더 큰 양수 방향으로 만드는 학습**이다.

| Margin | Sigmoid | DPO Loss |
|---:|---:|---:|
| 음수 | 0.5 미만 | 큼 |
| 0 | 0.5 | 약 0.693 |
| 양수 증가 | 0.5 초과 | 감소 |
| 매우 큰 양수 | 1에 근접 | 0에 근접 |

# 5. `detach()`는 GPU 메모리를 삭제하는 기능이 아니다

`reference_logps.detach()`를 GPU 메모리와 관련된 코드로 혼동했다.

`detach()`의 역할은 Tensor를 Autograd 계산 그래프에서 분리하는 것이다.

즉:

`reference_logps.detach()`  
→ Reference 점수 방향으로 Gradient가 흐르지 않도록 함

Reference는 DPO 학습에서 **변경할 대상이 아니라 비교 기준**이다.

따라서 Reference 점수에는 Gradient가 필요하지 않는다.

`detach()`는 다음 기능이 아니다.

- GPU 메모리 삭제
- CPU로 이동
- Tensor 삭제
- dtype 변경

GPU에서 CPU로 옮기려면 `.cpu()`와 같은 별도 처리가 필요하다.

# 6. Reference 점수를 미리 계산할 수 있는 이유

이번 DPO 구현에서는 Reference Model을 Policy Model과 동시에 GPU에 계속 올려두지 않는다.

Reference Model과 학습용 `chosen/rejected` 쌍이 모두 고정되어 있기 때문이다.

따라서 학습 전에:

`Reference Model + chosen/rejected → reference_scores 계산 → 저장`

이후 DPO 학습에서는 저장된 Reference 점수와 현재 Policy 점수만 비교한다.

Reference 점수를 다시 계산해야 하는 경우는 입력 조건이 달라졌을 때이다.

- Reference Model 변경
- Tokenizer 변경
- Chat Template 변경
- Prompt 변경
- chosen/rejected 변경
- 토큰화 또는 Mask 방식 변경

# 7. `beta`와 Learning Rate는 역할이 다르다

`beta`와 Learning Rate를 둘 다 학습 강도와 관련된 값으로만 생각하면 혼동하기 쉽다.

## Beta

`beta`는 DPO 목적함수에서 상대 점수 차이를 얼마나 크게 반영할지 결정한다.

$$m=\beta\times\mathrm{상대점수차이}$$

따라서 `beta`를 변경하면:

- Margin 크기
- DPO Loss
- Loss의 Gradient

에 영향을 줄 수 있다.

## Learning Rate

Learning Rate는 계산된 Gradient를 이용해 실제 모델 파라미터를 얼마나 크게 갱신할지 결정한다.

| 항목 | 역할 |
|---|---|
| `beta` | DPO 목적함수의 상대 선호 강도 조절 |
| Learning Rate | Optimizer의 가중치 갱신 크기 조절 |

`beta`는 Learning Rate가 아니다.

# 8. Train DPO Loss 감소만으로 모델이 좋아졌다고 판단할 수 없다

Train 선호쌍에서:

- DPO Loss 감소
- 48개 모두 양수 Margin

이 되었다면 확인할 수 있는 것은 다음뿐이다.

> 학습한 Train 선호쌍에서 Policy가 Reference보다 chosen을 rejected에 비해 상대적으로 더 선호하게 되었다.

이것만으로 다음을 보장할 수는 없다.

- chosen의 절대 확률 증가
- Dev 성능 향상
- 실제 답변 품질 향상
- JSON 형식 유지
- 근거 기반 답변 향상

따라서 DPO 결과는 최소한 다음을 함께 확인해야 한다.

1. `margin`과 DPO Loss
2. `chosen/rejected`의 절대 log-prob 변화
3. Dev 자유 생성 결과
4. 출력 형식 정상 여부
5. 근거가 충분한데 답변을 피하는 과잉 보류 여부
6. 근거가 부족한데 임의로 답하는 문제 여부

핵심은 **Train 목적함수 최적화와 실제 생성 품질은 별개로 검증해야 한다는 것**이다.

# 오늘의 핵심 정리

- DPO 응답 점수는 확률이 아니라 **응답 토큰 로그확률의 합**
- Margin은 `chosen`의 절대 점수가 아니라 **Reference 대비 chosen-rejected 상대 점수 변화**
- `Margin → Sigmoid → DPO Loss` 순서로 계산
- Margin이 커질수록 DPO Loss는 작아짐
- `detach()`는 GPU 메모리 삭제가 아니라 **Gradient 흐름 차단**
- `beta`는 목적함수의 선호 강도, Learning Rate는 실제 파라미터 갱신 크기
- Train Loss와 Margin이 좋아져도 **Dev 생성 품질 향상을 보장하지 않음**
