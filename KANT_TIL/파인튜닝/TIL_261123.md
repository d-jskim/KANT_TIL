# 2026.11.23 TIL — QLoRA 학습

## 1. GPU와 메모리

- **NVIDIA T4와 L4**
  - L4는 T4보다 최신 GPU로, VRAM 용량과 AI 연산 성능이 높음.
  - T4: VRAM 16GB, Native BF16 미지원
  - L4: VRAM 24GB, Native BF16 지원
- **VRAM(Video RAM)**: GPU가 모델 가중치, 기울기, 중간 연산 결과 등을 저장하는 메모리
- GPU 성능과 VRAM 용량은 다른 개념이며, VRAM이 크다고 학습 속도가 비례하여 증가하는 것은 아님.

## 2. 가중치 저장과 부동소수점

- **Bit·Byte**: 데이터 크기의 단위
- **FP32·BF16**: 실수를 표현하는 부동소수점 자료형
  - FP32: 32비트, 가수부 23비트
  - BF16: 16비트, 가수부 7비트
  - 지수부는 모두 8비트로 수치 표현 범위가 유사함.
- BF16은 FP32 대비 가중치 저장 공간이 절반이지만 수치 정밀도가 낮음.
- 자료형을 변경해도 가중치 개수는 달라지지 않음.
- 저장 정밀도, 계산 정밀도, 학습 여부는 각각 구분해야 함.

## 3. Codebook과 NF4 양자화

### 양자화 처리 순서

1. 원본 가중치의 블록별 절댓값 최댓값으로 Scale 계산
2. Scale로 나누어 -1~1 범위로 정규화
3. 코드북의 대표값과 비교하여 가장 가까운 값 선택
4. 선택한 대표값의 인덱스와 Scale 저장
5. 연산 시 인덱스와 Scale로 근사 가중치 복원

### 헷갈렸던 개념

- **Codebook**: 연속적인 모든 실수값이 아니라 제한된 대표값을 저장한 집합
- **Index**: 대표값 자체가 아니라 해당 대표값을 가리키는 번호
- **NF4**: 16개 대표값 중 하나를 4비트 인덱스로 표현
- 2비트 실습 예제는 대표값 4개를 사용하며, 실제 NF4와 구분 필요
- 서로 다른 원본 가중치가 동일한 대표값을 선택할 수 있으므로 양자화 오차 발생

### 저장 구조

- 원본 가중치를 개별 실수로 저장하는 대신 4비트 인덱스로 저장하여 메모리 절감
- `torch.uint8`: 4비트 코드 두 개를 하나의 8비트 컨테이너에 저장
- 코드북과 블록별 Scale은 복원을 위해 별도로 필요

## 4. 양자화 오차와 학습 손실의 차이

- **양자화 오차(Quantization Error)**: 원본 가중치와 복원된 근사 가중치의 차이
- **학습 손실(Training Loss)**: 모델의 예측과 모범 답변을 비교하여 계산하는 오차
- NF4 양자화 과정에서 손실된 원본 정보는 BF16이나 FP32로 변환해도 복구되지 않음.
- FP32로 변환하는 것은 원본 가중치를 되찾기 위한 것이 아니라 수치 표현의 정밀도를 확보하기 위한 것임.

## 5. QLoRA의 저장·계산·학습 구분

### 저장(Storage)

- 기반 모델의 양자화 대상 가중치를 NF4로 압축 저장
- 4비트 인덱스와 블록별 Scale 관리

### 계산(Computation)

- 인덱스와 Scale로 근사 가중치 복원
- BF16 또는 FP32 계산 정밀도로 행렬 연산 수행
- 4비트 저장이 모든 연산을 4비트로 수행한다는 의미는 아님.

### 학습(Training)

- 양자화한 기반 모델의 가중치는 고정
- 기반 모델과 LoRA A·B의 연산 결과를 결합
- Loss 계산 및 역전파를 통해 LoRA A·B의 기울기 계산
- Optimizer는 LoRA A·B만 갱신

### 가중치 동결과 자료형

- `dtype`: 파라미터를 어떤 자료형으로 표현하는지 결정
- `requires_grad`: 자동미분을 통해 해당 파라미터의 기울기를 계산할지 결정
- FP32로 저장한다고 반드시 학습 대상이 되는 것은 아님.
- 기반 가중치가 고정되어도 입력 방향의 기울기 전달은 가능함.

## 6. prepare_model_for_kbit_training()

- 양자화된 기반 모델을 LoRA 학습에 적합하도록 준비하는 함수
- 기존 기반 파라미터를 동결하고 Gradient Checkpointing 등의 학습 준비 수행
- 이번 PEFT 버전에서는 비양자화 BF16/FP16 파라미터를 FP32로 변환할 수 있음.
- NF4 기반 가중치 전체를 FP32로 되돌리는 과정은 아님.
- 기반 모델을 준비한 이후 LoRA A·B를 추가해야 학습 대상이 적절히 설정됨.

## 7. Double Quantization과 실제 메모리

- **Double Quantization**: 가중치의 블록별 Scale을 다시 양자화하여 부가 저장량 절감
- 4비트 인덱스만으로는 원본 가중치의 근삿값을 복원할 수 없으므로 Scale 저장 필요
- 가중치 64개가 FP32 Scale 하나를 공유할 경우 가중치당 0.5비트의 추가 저장 비용 발생
- Scale 재양자화를 적용한 설명용 계산에서는 약 4.126953 bits/weight 사용
- 실제 GPU 메모리에는 비양자화 파라미터, LoRA, Gradient, Optimizer 상태, Activation 등이 추가로 존재

## 8. Unsloth

- **Unsloth**: LLM 파인튜닝의 GPU 연산과 메모리 효율을 개선하는 오픈소스 라이브러리
- LoRA·QLoRA와 경쟁하는 별도 학습 기법이 아니라 기존 파인튜닝을 최적화하는 도구
- Unsloth 사용만으로 모델 정확도가 자동으로 개선되거나 양자화 오차가 사라지는 것은 아님.

## 9. LoRA와 QLoRA 실험 결과에 대한 오답

### 잘못 이해한 부분

- QLoRA는 4비트 양자화를 사용하므로 LoRA보다 학습 메모리와 시간이 모두 줄어들 것이라고 판단함.

### 실제 실험 결과

| 항목 | LoRA | QLoRA |
|---|---:|---:|
| 최종 Dev Loss | 0.871658 | 0.975252 |
| 최대 Allocated 메모리 | 1.615 GiB | 1.637 GiB |
| 학습 시간 | 17.75초 | 78.38초 |
| 형식·인용 ID 통과 | 0/12 | 0/12 |

- QLoRA는 자체 학습 전보다 Dev Loss가 감소했지만 최종 Loss는 LoRA보다 높았음.
- 이번 실험에서는 QLoRA의 GPU 최대 메모리와 학습 시간도 개선되지 않았음.
- 양자화는 기반 가중치의 저장 효율을 높이지만, 전체 GPU 메모리나 학습 속도 개선을 보장하지 않음.
- 실제 효과는 모델 크기, 실행 환경, 비양자화 파라미터, 역양자화 연산 등의 영향을 받음.

## 10. 추가 학습이 필요한 개념

- 기반 가중치가 고정되어도 Gradient가 전달되는 원리
- GPU 최대 Allocated 메모리와 모델 가중치 저장량의 차이
- LoRA와 QLoRA의 실제 자원 효율 비교 기준

## 핵심 정리

- **저장:** Scale 정규화 → NF4 코드북 매핑 → 4비트 인덱스와 Scale 저장
- **계산:** 인덱스와 Scale로 근사 가중치를 복원하고 BF16/FP32로 연산
- **학습:** 기반 가중치는 고정하고 LoRA A·B만 갱신
- **검증:** QLoRA의 메모리 절약과 학습 성능은 이론적인 저장 비트 수가 아니라 실제 실험 결과로 판단
