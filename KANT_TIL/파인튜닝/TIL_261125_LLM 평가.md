# 2. 학습 중 헷갈린 개념 정리

## 2.1. 검사 결과 `False`와 실제 실패 건수의 차이

`inspect_response()`는 JSON 객체, 스키마, 인용 ID를 순차적으로 검사함.

JSON 파싱에 실패하면 다음과 같은 결과를 반환함.

```python
{
    "json_object": False,
    "schema_ok": False,
    "citation_ids_ok": False
}
```

세 값이 모두 `False`이지만 실제 검사 실패가 세 건 발생했다는 의미는 아님.

| 항목 | 반환값 | 실제 상태 |
|---|---|---|
| `json_object` | `False` | JSON 검사 실패 |
| `schema_ok` | `False` | 앞 단계 실패로 미검사 |
| `citation_ids_ok` | `False` | 앞 단계 실패로 미검사 |

- 함수가 처음에 모든 값을 `False`로 초기화하기 때문에 발생하는 결과
- JSON 파싱 실패 시 즉시 반환하므로 나머지 검사는 수행되지 않음
- 반환 딕셔너리의 `False` 개수와 실제 실패 건수를 구분해야 함

### 첫 실패 집계(First Failure Count)

- 응답마다 최초로 실패한 단계 한 건만 집계
- JSON 검사에서 실패한 응답은 `json_object` 실패 1건으로 기록
- 뒤의 검사 미수행 상태를 별도 실패 건수로 중복 집계하지 않음

## 2.2. 형식 검증과 업무 의미 검증의 차이

JSON 객체 검사, 스키마 검사, 인용 ID 검사를 모두 통과했더라도 업무 판단이 정확한 것은 아님.

예를 들어 다음과 같은 경우가 있었음.

- 숙박비 한도: 65,000원
- 질문 금액: 70,000원
- 모델 답변: 한도 이하이므로 승인 불필요

이 응답은 JSON 구조와 인용 ID가 모두 정확할 수 있지만 금액 비교가 잘못됨.

| 평가 | 확인 대상 | 한계 |
|---|---|---|
| JSON 검사 | 파싱 가능한 JSON 객체 여부 | 업무 내용 검증 불가 |
| 스키마 검사 | 필드·타입·상태 규칙 | 판단의 정확성 검증 불가 |
| 인용 ID 검사 | 허용된 문서 ID 사용 여부 | 문서가 답변을 지지하는지 검증 불가 |
| 업무 의미 검증 | 조건·수치·근거·결론의 정확성 | 별도 평가 기준 필요 |

- 형식 준수율과 업무 정답률은 서로 다른 평가 지표임
- 인용 문서 ID가 존재한다는 사실만으로 해당 문서가 답변을 뒷받침한다고 판단할 수 없음

## 2.3. JSON 검사 성공과 최종 형식 통과의 차이

QLoRA 평가 결과는 다음과 같았음.

| 검사 단계 | 통과 수 |
|---|---:|
| JSON 객체 검사 | 11/12 |
| 스키마 계약 검사 | 1/12 |
| 인용 ID 검사 | 0/12 |
| 최종 형식 통과 | 0/12 |

- JSON 11/12는 JSON 객체로 읽을 수 있는 응답이 11개라는 의미
- 최종 형식 0/12는 세 검사를 모두 통과한 응답이 없다는 의미
- 따라서 두 결과는 모순되지 않음
- 실패한 응답을 제외하지 않고 전체 Dev 12개를 분모로 유지해야 함

## 2.4. 검색 오류와 모델 생성 판단 오류의 차이

기존 평가에서는 질문에 필요한 근거 문서를 미리 제공했지만, 실제 서비스에서는 문서 검색 과정이 추가됨.

```text
[사용자 요청]
      |
      v
[입력 검증]
      |
      v
[문서 검색]
      |
      v
[SFT 모델 추론]
      |
      v
[출력 검증]
      |
      v
[API 응답]
```

- 문서 검색(Retrieval): 질문에 필요한 근거 문서 선택
- 모델 추론(Inference): 질문과 검색된 문서를 바탕으로 답변 생성
- API(Application Programming Interface): 요청 검증, 검색, 추론 및 결과 반환 연결

### 오류 발생 위치에 따른 구분

| 상황 | 우선 점검 대상 |
|---|---|
| 관련 문서를 검색하지 못함 | 문서 목록, 검색 조건, 필터 |
| 올바른 문서를 찾았으나 잘못 답변함 | 모델의 근거 해석 및 생성 판단 |
| JSON·스키마 위반 | 출력 계약 및 생성 결과 |
| 잘못된 요청 입력 | API 입력 검증 |

실제 실습에서는 75,000원 한도 문서를 정확히 검색했으나 SFT 모델이 80,000원을 한도 이하라고 판단함.

따라서 검색 실패가 아닌 생성 판단 오류로 구분해야 함.

## 2.5. HTTP 200과 업무 정답의 차이

FastAPI 예제에서는 요청 및 출력 검사 결과에 따라 서로 다른 HTTP 상태 코드를 반환함.

| HTTP 상태 | 실습 코드에서의 의미 |
|---|---|
| 422 | 입력 계약 위반 또는 입력 토큰 제한 위반 |
| 502 | 모델 출력 형식 또는 길이 종료 조건 실패 |
| 200 | 출력 계약과 길이 조건 통과 |

- HTTP 200이 반환되어도 업무 판단이 틀릴 수 있음
- API 정상 처리와 모델 답변 정확성은 별개
- 출력 형식이 정상이어도 수치 비교 및 업무 조건 적용 오류가 발생할 수 있음

## 2.6. 모델 평가 결과와 운영 승인 판단의 차이

Dev에서 좋은 결과를 보인 모델을 최종 평가 후보로 선정하더라도 운영에 적합하다고 확정할 수 없음.

- Dev(Validation): 모델 비교 및 후보 선택에 활용
- Test: 후보와 평가 조건을 고정한 후 최종 성능 검증에 활용
- 운영 승인(Deployment Approval): 알려진 오류와 실제 업무 적용 가능성 등을 별도로 검토

이번 실습에서는 SFT의 형식 준수율이 12/12였지만 초과 금액 판단 오류가 남아 있었음.

따라서 SFT를 최종 검증 후보로 선정하되 운영 승인은 보류함.

```text
[Dev 평가]
    |
    v
[후보 모델 선정]
    |
    v
[모델 및 평가 설정 고정]
    |
    v
[Test 최종 평가]
    |
    v
[운영 승인 별도 판단]
```

- Dev 성적을 최종 성능으로 해석하지 않을 것
- Test 평가 전에 후보와 생성 설정을 고정할 것
- 알려진 오류가 있는 상태에서 후보 선정과 운영 승인을 동일하게 판단하지 않을 것

# 3. 오늘의 핵심 정리

- Post-training은 아직 표준화되지 않은 영역이 존재하므로 새로운 문제 해결에 도전해 볼 것
- API 명세서 작성과 문서화, 사용자 인증·권한 및 악의적인 질문 대응 필요
- 내부망 환경에서는 외부 LLM API 사용 제약을 고려해 자체 LLM 구축 검토
- 실험 Config를 기록하고 프런트엔드에서 조회할 수 있도록 구현하는 방식 고려
- 검사 결과의 `False`는 실제 실패와 미검사 상태를 모두 포함할 수 있으므로 첫 실패 위치를 구분해야 함
- JSON·스키마·인용 ID 검증만으로 업무 판단의 정확성을 보장할 수 없음
- 검색 실패와 모델 생성 판단 오류는 서로 다른 단계에서 발생함
- HTTP 200은 업무 정답을 보장하지 않으며, Dev 후보 선정도 운영 승인을 의미하지 않음
