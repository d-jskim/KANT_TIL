

######  Q. 불균형 데이터. 어느 정도가 균형 데이터로 볼 수 있는지?
전체 데이터수 / 클래수 수 * 100(%) * 0.8
- 0.8은 80%

## 7-1. Fine-tuning 문제 정의

- Sequence Classification은 문장·문서 전체에 하나의 class를 예측하는 분류 문제이다.
- 문제 정의 시 입력, 출력, label 규칙, 성공 기준, 실패 리스크를 명확히 한다.
- `label 수`는 데이터 개수가 아니라 분류 가능한 `label 종류 수 = class 수`를 의미한다.
- `label2id`: label 이름 → 정수 ID
- `id2label`: 정수 ID → label 이름
- 클래스 불균형이 심하면 Accuracy가 높아도 소수 클래스에 대한 예측 성능은 낮을 수 있다.
- 데이터 누수 예: 동일 문장이 train과 validation/test에 동시에 존재하는 경우.

## 7-2. Dataset Split과 Label Mapping

- `Dataset`: 샘플들의 집합
- `DatasetDict`: `train`, `validation`, `test` 등의 split 이름을 key로 하고 각각의 `Dataset`을 value로 가지는 구조
- `seed`: 동일한 split을 재현하기 위한 설정
- `stratify_by_column`: split 간 label 분포를 비슷하게 유지
- Validation은 모델 선택·설정 조정에 사용하고 Test는 모든 선택이 끝난 뒤 최종 평가에 사용한다.
- train과 validation/test의 text 중복을 확인해 데이터 누수를 방지한다.
- `label_mapping.json`에는 `label2id`, `id2label` 같은 label mapping을 JSON 형식으로 저장할 수 있다.

## 7-3. Tokenization과 Data Collator

- 원본 text는 tokenizer를 거쳐 `input_ids`, `attention_mask` 등으로 변환된다.
- `tokenized_dataset`은 tokenization 결과와 `labels` 등을 가진 데이터셋이다.
- `DataCollatorWithPadding`은 여러 샘플을 하나의 batch Tensor로 묶고 현재 batch의 가장 긴 샘플에 맞춰 dynamic padding을 수행한다.
- 흐름: 원본 text → `tokenized_dataset` → `data_collator` → batch → model
- `padding="max_length"`는 모든 샘플을 지정한 최대 길이까지 padding한다.
- Dynamic padding은 batch별 최장 샘플에 맞추므로 불필요한 padding을 줄일 수 있다.
- `remove_columns`는 불필요한 문자열 컬럼이 Trainer나 Collator로 전달되어 오류가 발생하는 것을 막는다.
- 원본 text를 제거하면 오류 분석 시 원문을 바로 확인하기 어렵다는 단점이 있다.
- `input_ids`, `attention_mask`의 일반적인 shape은 `[B, L]`, `labels`는 `[B]`이다.

## 7-4. Sequence Classification Model

- Transformer base model은 각 토큰의 문맥 표현을 만든다.
- Classification Head는 문장 전체를 대표하는 표현을 이용해 class 수만큼 logits를 생성한다.
- logits shape은 `[B, C]`이다.
  - `B`: batch size
  - `C`: class 수
- 예: batch 4개, class 7개 → logits shape `[4, 7]`
- `argmax(dim=-1)`은 각 샘플에서 가장 큰 클래스 index 하나를 선택하므로 `[B, C] → [B]`가 된다.
- `id2label`, `label2id`를 model config에 저장하면 예측 ID와 label 이름의 대응 관계를 모델과 함께 보존할 수 있다.
- labels를 모델에 함께 전달하면 Sequence Classification 모델이 loss를 계산해 반환할 수 있다.
- 학습 중에도 매 forward마다 logits가 생성된다.
- `CrossEntropyLoss`는 내부적으로 log-softmax를 포함하므로 loss 계산 전에 logits에 softmax를 직접 적용하지 않는다.
- 추론 시 확률을 해석하고 싶을 때 `softmax → probabilities → argmax` 순서로 사용한다.
- 모델과 batch Tensor는 같은 device에 있어야 한다.
- GPU는 대규모 Tensor 수치 연산에 특화되어 있고, CPU는 Python `dict`, 문자열, 일반 객체 처리에 적합하다.
- 따라서 GPU에서 `argmax`까지 계산한 뒤 예측 ID를 CPU로 가져와 `id2label` 같은 Python 자료구조에서 label 이름을 조회할 수 있다.
- `.cpu()`만 사용하면 여전히 Tensor이며, `.tolist()`나 `int()`를 사용해야 Python 자료형으로 변환된다.

## 7-5. Metric과 Confusion Matrix

- Accuracy: 전체 샘플 중 맞힌 비율
- Precision: 특정 클래스로 예측한 것 중 실제로 맞은 비율
- Recall: 실제 특정 클래스 샘플 중 모델이 찾아낸 비율
- F1: Precision과 Recall을 함께 고려하는 지표
- Macro-F1: 클래스별 F1을 동일한 비중으로 단순 평균
- `precision_recall_fscore_support()`는 `precision`, `recall`, `f1`, `support`를 반환한다.
- `support`는 각 클래스의 실제 정답 샘플 수인 지지도이다.
- `average="macro"`는 Precision, Recall, F1 각각에 클래스별 단순 평균을 적용한다.
- `zero_division=0`은 metric 계산 시 분모가 0인 경우 해당 값을 0으로 처리한다.
- scikit-learn metric 함수는 일반적으로 `정답, 예측값` 순서로 입력한다.
- PyTorch loss 함수는 일반적으로 `예측값, 정답` 순서로 입력한다.
- Confusion Matrix:
  - 위쪽 = prediction
  - 왼쪽 = true label
  - 각 셀의 숫자 = 해당 실제 label과 예측 label 조합의 샘플 수
  - 대각선 = 정답
  - 대각선 밖 = 오분류
- `compute_metrics`는 Trainer의 evaluation 또는 prediction 단계에서 predictions와 labels를 받아 metric을 계산한다.

## 7-6. TrainingArguments와 Trainer

- `TrainingArguments`: batch size, epoch, learning rate, evaluation, logging, checkpoint 저장 등의 학습 조건을 담는 설정 객체
- Hyperparameter는 결과에 영향을 주므로 실험 재현과 비교를 위해 기록해야 한다.
- `Trainer`는 model, dataset, tokenizer, data collator, metric 등을 연결해 학습·평가·저장 루프를 실행한다.
- `metric_for_best_model="macro_f1"`을 사용하려면 `compute_metrics`가 `macro_f1` key를 반환해야 한다.
- CUDA OOM은 GPU 메모리가 부족해 연산을 수행하지 못하는 오류이다.
- OOM 발생 시 batch size나 `max_length`를 줄이거나 `gradient_accumulation_steps`를 사용할 수 있다.
- `gradient_accumulation_steps`는 여러 mini-batch의 gradient를 누적한 뒤 한 번 parameter를 업데이트하는 방식이다.
- `validation`, `evaluation`, `model.eval()`, `test`는 서로 다르다.
  - Validation: 모델 선택·조정용 데이터
  - Evaluation: 성능을 평가하는 과정
  - `model.eval()`: Dropout 등의 동작을 평가 모드로 바꾸는 함수
  - Test: 모든 선택이 끝난 뒤 최종 성능 평가용 데이터

## 7-7. Fine-tuning과 Checkpoint

- Fine-tuning은 사전학습 모델의 파라미터를 특정 데이터셋과 태스크에 맞게 추가 학습하는 과정이다.
- `checkpoint`: 학습 중 특정 step 또는 epoch 시점의 모델 상태 저장본
- `best model`: validation metric 기준으로 가장 성능이 좋은 checkpoint
- `final model`: 학습과 모델 선택이 끝난 뒤 실제 사용할 모델로 최종 확정해 저장한 산출물
- Best model을 최종 채택하면 `best model = final model`이 될 수 있다.
- `load_best_model_at_end=True`는 학습 마지막 시점의 모델이 항상 가장 좋은 모델은 아니므로 학습 종료 후 best checkpoint를 다시 불러오기 위해 사용한다.
- Train loss는 감소하지만 validation loss가 증가하면 과적합을 의심한다.
- 작은 데이터에 일부러 overfit시키는 sanity check는 학습 파이프라인이 정상적으로 작동하는지 빠르게 확인하는 방법이다.
- 작은 데이터도 외우지 못하면 데이터, label, loss, gradient, optimizer 연결 등을 먼저 확인한다.
- `sanity check`는 기본적인 정상 동작 여부를 확인하는 점검이다.
- 모델 저장 시 tokenizer도 함께 저장해야 동일한 vocab, token ID mapping, special token, padding/truncation 규칙을 다시 사용할 수 있다.

## 7-8. Error Analysis와 최종 평가

- Error Analysis는 틀린 예측 사례를 직접 확인해 모델의 실패 패턴과 원인을 분석하는 과정이다.
- Metric은 전체 성능을 요약하지만 어떤 샘플에서 왜 틀렸는지는 알려주지 않는다.
- Confidence는 모델이 예측한 클래스에 부여한 확률적 점수이며 정답을 보장하지 않는다.
- 높은 confidence 오류는 잘못된 패턴을 강하게 학습했거나 label 오류가 있을 가능성을 확인한다.
- 낮은 confidence 오류는 문장이 애매하거나 클래스 경계가 불명확할 가능성을 확인한다.
- Test 결과를 보고 반복적으로 모델 설정을 변경하면 Test가 사실상 Validation 역할을 하게 되어 최종 평가가 편향될 수 있다.
- Confidence 임계값도 Validation에서 결정하고 Test는 최종 평가에 사용한다.
- Confusion Matrix에서 특정 두 클래스의 혼동이 많으면 label 정의, 데이터 품질, 추가 데이터, label 체계를 검토한다.
- Fine-tuning 리포트에는 문제 정의, 데이터와 split, label 규칙, 모델과 tokenizer, 학습 설정, metric, checkpoint, 오류 분석, 한계와 개선안을 포함한다.
- Data Card는 데이터 출처, 구성, label, 한계, 라이선스 등을 정리한 문서이다.
