
## 실무 참고 사항 (튜터님 코멘트)

- Private LLM 및 RAG 서비스에서는 `system prompt`와 `instruction` 설계가 중요함
  - 모델이 사용할 근거의 범위
  - 답변 가능 여부 판단 기준
  - 출력 형식
  - 예외 상황 처리 기준 등을 구체적으로 정의할 필요가 있음
- 상세한 Instruction 설계와 함께 Prompt Injection, Jailbreak 등 모델 지시문을 우회하려는 공격에 대한 고려가 필요함
- 모델 출력은 지시한 형식을 항상 정확하게 따르지 않을 수 있으므로 후처리 검증 필요
  - 예: `status`는 `answered`, `insufficient`만 허용
  - 허용되지 않은 값이나 오탈자가 반환되면 `ValueError` 등의 예외 처리 필요
- 분기 처리는 필요한 경우에 명확하게 설계하되 과도한 분기는 지양
  - LLM을 이용해 코드를 생성하면 불필요하게 많은 예외 분기가 만들어질 수 있음
  - `rag_core.py`의 `validate_answer()`처럼 실제 요구사항을 기준으로 필요한 검증만 구성
- 테스트 케이스를 별도로 구성하여 정상·비정상·경계 상황 검증 필요
- RAG 품질 평가를 위한 평가 데이터셋을 직접 구축해야 하는 경우가 있음
  - LLM-as-a-Judge 방식으로 자동 평가 가능
  - 중요한 기준은 사람의 평가를 병행할 필요가 있음
  - 검색 성능과 최종 답변 품질을 구분하여 평가
- 검색 방식별 성능 비교 필요
  - BM25
  - Dense Retrieval
  - Hybrid Search
  - Re-ranking
  - Query Rewrite
  - 한 사례의 개선만으로 전체 성능 향상을 판단하지 않고 공통 평가 데이터셋으로 비교
- Private LLM 설계 시 데이터가 외부로 전달되는 경로를 명확히 파악해야 함
  - 외부 LLM API 사용 시 기업 내부 데이터가 외부 서비스로 전달될 가능성 검토
  - 민감정보, 사내 문서, 개인정보 등의 API 전달 여부를 보수적으로 판단
  - Private LLM의 목적과 데이터 보안 요구사항을 함께 고려
- sLLM 구축에서는 기반이 되는 Open-weight Model 확보 가능성과 라이선스·사용 제한을 검토해야 함
  - 기업이 모델 가중치를 공개하지 않거나 공개 범위를 제한하면 자체 sLLM 구축 선택지가 제한될 수 있음
  - 모델 공개 여부뿐 아니라 상업적 이용, 재학습, 배포 조건도 확인 필요
- 모델 및 AI 서비스 사용 과정에서 입력 데이터가 향후 모델 개선이나 학습에 활용될 가능성이 있는지 서비스 정책 확인 필요
  - 특히 기업 데이터가 포함된 경우 데이터 보관·학습·재사용 정책을 사전에 검토

## 1. Context 구성

- Retriever 결과를 `chunk_id` 기준으로 중복 제거
- 같은 `document_id`라도 서로 다른 청크는 다른 사실을 포함할 수 있으므로 유지
- Context에는 `[S1]`, `[S2]` 형태의 출처 라벨 부여
- 라벨은 실제 Context에 포함된 근거 기준으로 생성
- Context 예산 초과 청크는 잘라 넣지 않고 건너뜀
- 근거 누락 원인 구분
  - 검색 단계 누락: `k`
  - Context 단계 누락: `max_chars`
- 실습은 문자 예산 사용
- 실제 서비스는 tokenizer 기반 토큰 예산 필요
- 시스템 지시, 질문, Context, 대화 기록, 출력 공간까지 함께 고려

## 2. 2-Step RAG

- 처리 흐름
  - `prepare`
  - `invoke_model`
  - `finish`
- `prepare`
  - 검색
  - Context 구성
  - Sources 구성
- `invoke_model`
  - 모델 호출
  - Draft 생성
- `finish`
  - 응답 검증
  - 출처 연결
  - 최종 응답 생성
- JSON Schema
  - 출력 필드와 자료형 제한
  - 형식은 검증 가능
  - 사실성은 별도 검증 필요

## 3. Citation 검증

- `context`
  - 모델이 읽는 근거 문자열
- `sources`
  - 출처 ID와 실제 문서 정보 연결
- 모델이 URL을 직접 생성하지 않도록 설계
- 저장된 `source_url`을 이용해 실제 출처 연결
- 검증 상태
  - `unknown_source`
    - 현재 Context에 없는 출처 ID
  - `quote_not_found`
    - 출처는 있지만 발췌문이 원문에 없음
  - `extractive_match`
    - 답변 문장과 발췌문이 동일
  - `review_meaning`
    - 표현이 달라 의미 검토 필요
- 출처가 맞는 것과 답변 내용이 맞는 것은 별도 검증 필요

## 4. 근거 부족 시 답변 보류

- 검색 결과 존재 여부와 답변 가능 여부를 분리
- 관련 문서가 검색돼도 질문에 필요한 사실이 없을 수 있음
- 근거가 부족하면 추측하지 않고 `insufficient`
- 보류 시 부족한 내용과 필요한 자료를 구체적으로 안내
- 상태 구분
  - `insufficient`
    - 근거 부족
  - `system_error`
    - HTTP, 서버 연결 오류
  - `invalid_output`
    - 응답 파싱 또는 검증 실패
- 규정에 없는 내용은 `지원하지 않는다`고 단정하지 않고 추가 확인 필요로 처리

## 5. BM25

- 키워드 및 토큰 일치 기반 검색
- 주요 요소
  - `f(t,d)`: 청크 내부 토큰 빈도
  - `df`: 해당 토큰이 등장한 청크 수
  - `IDF`: 희귀한 토큰에 높은 가중치
  - `k1`: 토큰 빈도 증가에 따른 점수 포화 조절
  - `b`: 문서 길이 정규화 조절
- 단순 토큰화 시 조사 차이에도 다른 토큰으로 처리될 수 있음
  - `영수증`
  - `영수증을`
  - `영수증으로`
- 검색 실패가 곧 자료 부재를 의미하지 않음

## 6. Dense Retrieval

- Embedding 기반 의미 검색
- 질문과 청크를 Vector로 표현
- 표현이 달라도 의미가 가까우면 검색 가능
- 관련 문서를 찾았다고 정답 청크까지 찾았다고 볼 수 없음
- `document_id`와 실제 정답이 들어 있는 `chunk_id`를 구분해야 함

## 7. BM25와 Dense 비교

- BM25
  - 단어 일치에 강함
  - 고유명사, 정확한 표현, 코드, 숫자 검색에 유리
- Dense
  - 의미 유사도에 강함
  - 표현이 다른 질문에 유리
- 두 검색기의 원시 점수 척도는 서로 다름
- BM25 점수와 Dense 유사도 점수를 그대로 합산하지 않음

## 8. Hybrid Search와 RRF

- Hybrid Search
  - BM25와 Dense 후보를 함께 사용
- RRF
  - Reciprocal Rank Fusion
  - 원시 점수 대신 각 검색기의 순위를 이용
- 특정 검색기에 없는 후보
  - 해당 검색기에서는 기여도 없음
- 동일 청크의 기여도
  - `chunk_id` 기준으로 합산
- 동점 처리
  - `chunk_id` 순으로 고정
- `contributions`
  - 어떤 검색기에서 몇 위로 기여했는지 추적
- 후보 수와 최종 반환 수를 구분
  - 후보 수: 정답 발견 기회
  - 최종 개수: LLM에 전달할 정보량
- 후보 단계에서 빠진 근거는 RRF가 복구할 수 없음

## 9. Re-ranking

- Dense Retrieval
  - Bi-Encoder
  - 질문과 문서를 각각 Embedding
  - 전체 후보 검색에 적합
- Re-ranking
  - Cross-Encoder
  - 질문과 청크를 함께 입력
  - 후보별 관련성 재평가
- Cross-Encoder 특징
  - 질문마다 다시 계산
  - 전체 DB 검색보다 소수 후보 재정렬에 적합
- `logit`
  - 원시 관련성 점수
  - 확률이 아님
  - 음수도 가능
  - 같은 질문의 후보끼리 비교
- `max_length`
  - 질문과 청크를 합친 입력 토큰 제한
- `batch_size`
  - 한 번에 처리하는 질문-청크 쌍의 수
- Re-ranker는 후보에 없는 근거를 새로 찾을 수 없음
- 이전 순위와 새 순위를 함께 기록해 재정렬 효과 확인

## 10. Query Rewrite와 Multi-Query

- Query Rewrite
  - 원래 질문을 검색 친화적으로 재작성
  - 1개 질문 → 1개 재작성 질문
- Multi-Query
  - 같은 의도의 여러 검색 표현 생성
  - 1개 질문 → 여러 검색 질문
- 질문 분해
  - 하나의 질문을 서로 다른 하위 질문으로 분리
- Rewrite 원칙
  - 사용자 의도 유지
  - 없는 숫자나 조건 추가 금지
  - 정답을 미리 질문에 삽입하지 않음
- 여러 검색 결과는 `chunk_id` 기준으로 중복 제거
- 검색 문장 자체의 중복은 순서를 유지하며 제거
- 검색 표현이 많아지면 정답 청크와 함께 잡음도 늘어날 수 있음
- 최종 답변과 Re-ranking은 사용자의 원질문 기준으로 수행

## 11. 오늘 복습에서 헷갈린 내용

- Context 예산 초과 시 해당 청크만 건너뜀
- S1, S2는 실제 Context 포함 순서 기준
- `quote_not_found`와 `review_meaning` 구분
- BM25 검색 실패와 자료 부재 구분
- `df`, `k1`, `b` 역할
- RRF는 원시 점수가 아니라 순위를 사용
- 한 검색기에 없는 후보는 해당 검색기 기여도 없음
- RRF 동점 시 `chunk_id` 기준 정렬
- 후보 단계에서 빠진 근거는 RRF나 Re-ranking으로 복구 불가
- 관련 문서를 찾는 것과 정답 청크를 찾는 것은 다름
- Cross-Encoder의 `max_length`는 입력 토큰 제한
- HTTP 오류는 `system_error`
- 출력 파싱·검증 오류는 `invalid_output`

## 12. 핵심 정리

- RAG 품질은 검색 모델 하나로 결정되지 않음
- 필요한 청크를 검색하는 것부터 중요
- 검색 결과를 적절한 Context로 구성해야 함
- 출처와 답변 의미를 각각 검증해야 함
- 근거가 부족하면 추측하지 않고 보류해야 함
- 검색 성능 개선은 단계별 문제를 확인한 뒤 적용
- BM25 → Dense → RRF → Re-ranking → Query Rewrite를 무조건 모두 적용하는 것이 아니라, 어느 단계에서 근거가 빠지는지 먼저 확인하는 것이 중요
