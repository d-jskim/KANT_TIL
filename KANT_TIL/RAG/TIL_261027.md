
## 튜터님 코멘트(실무)

- Golden Dataset은 문서 단위뿐 아니라 **청크 단위**까지 평가 기준을 세밀하게 둘 수 있음
  - 예: `relevant_document_ids`로 정답 문서를 지정
  - 실무에서는 필요에 따라 `chunk_id` 수준까지 검증하여 실제 정답 근거 청크가 검색되었는지 확인 가능
  - 문서를 찾았더라도 정답이 포함된 청크를 찾지 못할 수 있으므로 평가 단위를 명확히 정의할 필요가 있음

```python
{"question_id": "q10", "question": "교육비 정산 증빙은 무엇인가요?", "relevant_document_ids": ["education"], "reference": "수료증+영수증", "answerable": true, "split": "dev"}
```

- `answer_review`에서 여러 `answer` 객체를 각각 LLM으로 평가하면 전체 평가 시간이 길어질 수 있음
  - `async/await`와 `asyncio.gather()`를 활용해 여러 평가 요청을 비동기적으로 동시에 처리 가능
  - LLM API 호출처럼 I/O 대기 시간이 큰 작업에서 전체 대기 시간을 줄이는 데 효과적

- 성능 비교 실험에서는 변인 통제 설계가 중요함
  - 비교하려는 요소 외의 조건은 동일하게 유지
  - 검색 방식, `k`, 모델, Prompt, 평가 데이터셋 등의 조건을 통제해야 결과를 공정하게 비교 가능

- 실험 결과는 정확도 지표만 보지 않고 여러 관점에서 함께 비교
  - 품질 지표
  - 처리 시간
  - API 비용
  - 실제 서비스에서는 성능과 비용, 응답 속도의 균형을 함께 고려

- RAG는 목적과 데이터 특성에 따라 다양한 형태로 확장 가능
  - Agentic RAG
  - Graph RAG
  - Multimodal RAG
  - 단순 Vector Retrieval을 넘어 에이전트, 그래프 구조, 이미지·문서 등 다양한 데이터 형태를 결합하는 방향으로 확장

- 모든 서비스가 모델 자체를 개발하거나 튜닝하는 것은 아님
  - 스타트업 등에서는 기존 LLM을 활용하면서 RAG 파이프라인과 검색 로직을 자체적으로 개선해 성능을 높이기도 함
  - 검색 품질, 데이터 구조, Chunking, Hybrid Search, Re-ranking 등 RAG 설계 자체가 주요 경쟁력이 될 수 있음

## 1. Golden Dataset

- RAG 시스템을 평가하기 위해 미리 만들어 두는 정답 기준 데이터
- 원문 문서를 기준으로 질문별 정답 정보를 사전에 정의
- LLM 답변만 평가하는 것이 아니라 검색 결과 평가에도 활용
- 검색 시 Golden 자체를 입력으로 사용하는 것이 아니라 실제 검색 결과와 비교하는 기준으로 사용

### 주요 구성 항목

- `question`: 평가할 질문
- 정답 `document_id`
- 정답 `chunk_id`
- 참고 답변
- 답변 가능 여부
- `dev`, `test` 등의 데이터 분할

### 검색 평가에서의 활용

```text
질문
  ↓
Retriever
  ↓
검색 결과
  ↓
Golden 정답과 비교
```

- 정답 문서 또는 정답 청크가 검색되었는지 확인
- 검색 단계와 생성 단계를 별도로 평가 가능
- 검색에서 정답 근거를 찾지 못했다면 생성 모델 이전 단계의 문제로 판단 가능

## 2. Hit

- 정답 문서 또는 청크가 Top-K 검색 결과에 포함되었는지 평가하는 지표
- 정답을 하나라도 찾았는지에 초점

예:

```text
Golden 정답: education

Top-3 검색 결과:
1. travel
2. education
3. meal

→ Hit@3 = 1
```

- Top-K 안에 정답 존재 → Hit
- Top-K 안에 정답 없음 → Miss

## 3. Recall

- 찾아야 하는 전체 정답 중 실제 검색 결과에서 얼마나 찾았는지 평가
- 정답 근거가 여러 개인 경우 검색기가 얼마나 놓치지 않았는지 확인 가능

예:

```text
Golden 정답 청크: 4개
검색된 정답 청크: 3개

Recall@K = 3 / 4
```

### Hit과 Recall 차이

- Hit
  - 정답을 하나라도 찾았는가
- Recall
  - 찾아야 할 정답 전체 중 얼마나 찾았는가

따라서 정답 근거가 여러 개일 경우 Recall이 검색 누락 정도를 더 자세히 보여줄 수 있음

## 4. RAGAS

- RAG 시스템의 품질을 평가하기 위한 평가 프레임워크
- LLM이 생성한 최종 답변만 평가하는 것은 아님
- 검색된 Context와 생성된 Answer를 여러 관점에서 평가 가능

대표적인 평가 관점

- Context Recall
- Context Precision
- Faithfulness
- Answer Relevancy

### 평가 범위 구분

```text
Retriever
  ↓
Hit / Recall
  ↓
Context
  ↓
LLM
  ↓
Answer
  ↓
RAGAS
```

- `Hit`, `Recall`
  - Retriever의 검색 성능 평가에 활용
- `RAGAS`
  - Retrieval과 Generation을 포함한 RAG 품질 평가에 활용

## 5. Knowledge Graph

문서 안의 정보를 단순 텍스트로만 저장하지 않고 Entity와 Relationship 형태로 연결하여 표현할 수 있음

이번 실습에서는 다음과 같은 관계를 정의

```python
relations = [
    ("travel", "영수증", "제출", "숙박 정산"),
    ("education", "영수증", "제출", "수강 완료 후"),
    ("education", "수료증", "제출", "수강 완료 후"),
    ("meal", "영수증", "제출", "출장 식비 정산"),
    ("travel", "담당 임원", "승인자", "한도 초과 숙박 예약 전 서면 승인"),
    ("education", "팀장", "승인자", "수강 전"),
    ("leave", "팀장", "승인자", "휴가 시작 3영업일 전"),
    ("vpn", "관리자", "승인자", "VPN 계정 발급"),
]
```

하나의 관계는 다음과 같이 해석 가능

```text
travel
  └─ 제출 / 숙박 정산 → 영수증
```

```text
travel
  └─ 승인자 / 한도 초과 숙박 예약 전 서면 승인 → 담당 임원
```

## 6. Graph의 Entity 구분

Neo4j처럼 Node를 역할별 Entity 유형으로 구분할 수 있음

### Policy

- `travel`
- `education`
- `meal`
- `leave`
- `vpn`

### Evidence

- 영수증
- 수료증

### Person

- 담당 임원
- 팀장
- 관리자

### Document

- 각 규정의 실제 원문
- `source_url`을 통해 원문 출처와 연결

Entity 유형을 구분하면 그래프에서 각 노드가 어떤 의미를 가지는지 쉽게 확인할 수 있음

## 7. Relationship과 Condition

Node 사이의 연결에는 단순 관계명뿐 아니라 관계가 성립하는 조건도 함께 저장할 수 있음

예:

```text
education → 팀장
```

- 관계: 승인자
- 조건: 수강 전

```text
leave → 팀장
```

- 관계: 승인자
- 조건: 휴가 시작 3영업일 전

두 관계 모두 `팀장`을 가리키지만 적용 조건은 다름

따라서 Knowledge Graph에서는 같은 Entity가 연결되더라도 `condition`을 함께 보존해야 의미가 섞이지 않음

## 8. Graph에 출처 저장

그래프의 관계에는 원문을 확인할 수 있는 출처 정보도 함께 저장 가능

주요 속성

- `relation`
- `condition`
- `source_document_id`
- `source_url`

예:

```text
travel
  │
  ├─ relation: 승인자
  ├─ condition: 한도 초과 숙박 예약 전 서면 승인
  ├─ source_document_id: travel
  └─ source_url: 원문 URL
```

그래프에서 관계를 찾은 뒤 실제 원문까지 다시 확인할 수 있도록 설계 가능

## 9. Graph 탐색

하나의 Entity를 중심으로 연결된 여러 규정을 탐색할 수 있음

예:

```text
travel ──────┐
education ───┼──→ 영수증
meal ────────┘
```

`영수증`을 기준으로 탐색하면 영수증 제출을 요구하는 여러 규정을 한 번에 찾을 수 있음

이후 각 규정의 다른 관계를 다시 따라갈 수도 있음

```text
영수증
   ↑
   │ 제출
 travel
   │
   └─ 승인자 → 담당 임원
```

즉 하나의 Entity를 매개로 여러 정보 사이의 관계를 연결하여 탐색할 수 있음

## 10. NetworkX와 GraphRAG

현재 실습에서는 사람이 직접 정의한 관계를 이용해 NetworkX 그래프를 생성하고 탐색

```text
documents.json
    ↓
관계 직접 정의
    ↓
NetworkX DiGraph
    ↓
Entity / Relationship 탐색
```

또한 실제 GraphRAG 입력을 위해 문서를 TXT 파일로 저장

```text
documents.json
    ↓
문서별 TXT
    ↓
graphrag_demo/input
```

하지만 이 단계만으로 공식 GraphRAG가 실행된 것은 아님

아직 수행하지 않은 영역

- LLM 기반 Entity 추출
- Relationship 추출
- Graph Index 생성
- GraphRAG Query

따라서 현재 실습은 Graph 구조와 관계 탐색 원리를 이해하고, GraphRAG 입력 데이터를 준비하는 단계로 볼 수 있음

## 오늘의 핵심

- Golden Dataset은 검색 결과와 생성 결과를 평가하기 위한 정답 기준
- Hit은 정답을 하나라도 찾았는지, Recall은 전체 정답 중 얼마나 찾았는지를 평가
- RAGAS는 Retrieval과 Generation을 포함한 RAG 품질 평가에 활용
- Knowledge Graph는 정보를 Entity와 Relationship으로 연결하여 표현
- 동일한 Entity라도 관계 조건이 다를 수 있으므로 `condition`을 함께 저장해야 함
- 관계에는 `source_document_id`, `source_url`을 저장해 원문 근거까지 추적 가능
- NetworkX 그래프 탐색과 공식 GraphRAG 실행은 구분해야 함
