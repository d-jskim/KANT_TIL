
## 데이터 수집 원천

데이터를 수집할 수 있는 대표적인 원천은 다음과 같다.

- 공공데이터포털: `data.go.kr`
- AI Hub
- 민간 서비스
- 기업에서 제공하는 Open API
- CSV, JSON, PDF 등의 공개 데이터셋

기업마다 제공하는 API가 다르며, Bloomberg API처럼 전문 데이터를 제공하면서 비용이 발생하는 서비스도 있다.

## 데이터 수집 시 갱신 주기와 비용 고려

데이터를 수집할 때는 단순히 데이터를 가져올 수 있는지만 보는 것이 아니라 데이터의 갱신 주기와 비용을 함께 고려해야 한다.

- 실시간성이 필요한 데이터인가?
- 하루 또는 한 달에 한 번 갱신해도 되는가?
- API 호출마다 비용이 발생하는가?
- 호출 횟수 제한이 있는가?
- 데이터를 내부에 저장하여 재사용할 수 있는가?

실무에서는 기술적으로 구현 가능한 방법 중에서 비용과 운영 효율까지 고려하여 수집 방식을 결정해야 한다.

## 웹 크롤링과 API 수집의 차이

웹 크롤링은 웹페이지의 HTML 등을 읽어 필요한 데이터를 추출하는 방식이다.

API는 서비스 제공자가 정해 놓은 인터페이스를 통해 데이터를 요청하고 JSON 등의 구조화된 형식으로 전달받는 방식이다.

API가 공식적으로 제공된다면 웹페이지를 직접 크롤링하는 것보다 API를 사용하는 것이 일반적으로 더 안정적이다.

## 수집 전 확인할 네 가지

### 이용 조건을 확인했는가?

사이트나 데이터 제공자가 허용한 범위 안에서 데이터를 사용해야 한다.

확인할 내용:

- 상업적 이용이 가능한가?
- 저장할 수 있는가?
- 수정 및 가공할 수 있는가?
- 재배포할 수 있는가?
- 출처 표시가 필요한가?
- API 호출 횟수 제한이 있는가?

### `robots.txt`를 확인했는가?

웹사이트 운영자가 자동화된 프로그램의 접근을 허용하거나 제한하는 범위를 확인한다.

```text
User-agent: *
Disallow: /private/
Allow: /public/
```

`/private/`, `/public/`은 특별한 태그가 아니라 URL 경로의 예시이다.

`robots.txt`의 허용 여부와 데이터의 저작권 및 이용 허가는 별개의 문제이므로 각각 확인해야 한다.

### 개인정보가 포함될 가능성이 있는가?

수집하려는 데이터에 다음과 같은 정보가 포함되어 있는지 확인한다.

- 이름
- 전화번호
- 이메일
- 주소
- 위치 정보
- 건강 정보
- 금융 정보

특히 분석이나 질문에 필요하지 않은 개인정보라면 수집 대상에서 제외하는 것이 좋다.

### 저작권과 라이선스를 확인했는가?

인터넷에 공개된 데이터라고 해서 자유롭게 저장, 수정, 배포할 수 있는 것은 아니다.

데이터를 수집하기 전에 해당 데이터의 라이선스와 허용 범위를 확인해야 한다.

## 라이선스별 수정·가공·재사용 가능 범위 확인

Apache 2.0 등의 라이선스가 표시되어 있다면 해당 라이선스의 상세 조건을 확인해야 한다.

주요 확인 사항:

- 수정 가능한가?
- 가공 가능한가?
- 상업적으로 사용할 수 있는가?
- 재배포할 수 있는가?
- 원저작자 또는 출처를 표시해야 하는가?
- 추가적인 라이선스 조건이 존재하는가?

따라서 데이터를 다운로드할 수 있다는 사실과 데이터를 원하는 방식으로 재사용할 수 있다는 사실은 서로 다르다.

## API 또는 파일이 있으면 크롤링보다 우선 고려

공식 API나 다운로드할 수 있는 데이터셋이 존재한다면 웹 크롤링보다 해당 방법을 우선 고려한다.

```text
공식 API
    ↓
공식 데이터 파일
    ↓
필요한 경우 웹 크롤링 검토
```

API나 공식 데이터셋은 데이터 구조가 명확하고 이용 조건을 확인하기도 상대적으로 쉽다.

## 데이터 스냅샷과 과거 이력 보관 필요성

API가 현재 상태만 제공한다면 나중에 과거 상태를 다시 조회할 수 없을 수 있다.

예를 들어 오늘의 교육 신청 인원만 제공하는 API가 있다면 한 달 뒤 해당 API를 호출해도 오늘의 값을 알 수 없다.

따라서 과거 데이터가 필요한 경우 주기적으로 데이터를 저장해야 한다.

```text
9월 1일 → 데이터 저장
9월 2일 → 데이터 저장
9월 3일 → 데이터 저장
```

이처럼 특정 시점의 데이터를 저장한 것을 스냅샷이라고 볼 수 있다.

과거 변화가 필요한 질문이라면 현재 API를 호출하는 것만으로는 부족하고 주기적인 데이터 보관이 필요하다.

## RAG를 통한 근거 문서 기반 답변과 할루시네이션 완화

LLM은 실제 근거가 없는 내용을 생성하는 할루시네이션이 발생할 수 있다.

RAG는 질문과 관련된 문서를 먼저 검색하고 해당 문서를 근거로 LLM이 답변하도록 하는 방법이다.

```text
사용자 질문
    ↓
관련 문서 검색
    ↓
근거 문서 추출
    ↓
LLM에 질문과 근거 전달
    ↓
근거 기반 답변 생성
```

회사 규정, 정책, 매뉴얼처럼 정해진 문서를 근거로 답해야 하는 서비스에 활용할 수 있다.

## EDF/BDF와 생체 시계열 데이터

`EDF`는 `European Data Format`으로 EEG, ECG, EMG, 수면검사 등의 생체 시계열 신호를 저장하는 데 사용되는 파일 형식이다.

`BDF`는 `BioSemi Data Format`으로 EDF와 비슷하지만 더 높은 해상도의 신호를 저장할 수 있다.

대표적으로 EDF는 16-bit, BDF는 24-bit 신호를 저장할 수 있다.

`EEG`는 데이터의 종류이고 `EDF`, `BDF`는 이러한 데이터를 저장할 수 있는 파일 형식이다.

## 시계열 데이터를 전용 파일 포맷으로 저장하는 이유

시계열 데이터도 관계형 데이터베이스에 저장할 수 있다.

그러나 EEG처럼 여러 채널에서 초당 수백 번씩 측정하는 데이터는 매우 많은 측정값이 발생한다.

생체신호에는 측정값뿐 아니라 다음 정보도 함께 필요하다.

- 채널 이름
- 샘플링 주파수
- 측정 단위
- 측정 시작 시각
- 신호 보정 정보
- 여러 채널 간 동기화 정보

EDF와 BDF는 이러한 연속적인 다채널 신호를 효율적으로 저장하고 교환하기 위한 구조를 가지고 있다.

또한 시간축과 채널 정보가 함께 저장되므로 MNE, pyEDFlib 등의 라이브러리로 읽어 시계열 그래프를 생성하기도 편리하다.

## EDF/BDF와 DB의 역할 차이

EDF/BDF와 데이터베이스 중 하나만 사용해야 하는 것은 아니다.

실제 시스템에서는 다음과 같이 함께 사용할 수 있다.

```text
Database
├─ 환자 ID
├─ 검사 날짜
├─ 검사 종류
└─ EDF 파일 위치
        ↓
EDF/BDF
├─ 실제 생체신호
├─ 채널 정보
├─ 샘플링 정보
└─ 연속 측정값
```

DB는 데이터를 검색하고 관리하기 위한 정보를 저장하고, EDF/BDF는 실제 대용량 연속 신호를 저장하는 역할을 담당할 수 있다.

## HTTP Method의 안전성과 멱등성

안전성은 요청을 실행했을 때 서버의 데이터 상태를 변경하는지를 의미한다.

`GET`은 데이터를 조회하기 위한 요청이므로 안전한 메서드이다.

`POST`, `PUT`, `DELETE`는 서버의 데이터를 생성, 수정 또는 삭제할 수 있으므로 안전하지 않다.

멱등성은 동일한 요청을 여러 번 실행해도 최종 서버 상태가 한 번 실행한 것과 같은지를 의미한다.

- `GET`: 멱등
- `PUT`: 멱등
- `DELETE`: 멱등
- `POST`: 일반적으로 멱등하지 않음

핵심 차이는 다음과 같다.

```text
안전성 → 서버 상태를 변경하는가?
멱등성 → 여러 번 실행해도 최종 상태가 같은가?
```

## 429 Too Many Requests의 의미와 대응

HTTP 상태 코드 `429`는 `Too Many Requests`를 의미한다.

짧은 시간에 너무 많은 API 요청을 보내거나 정해진 호출 한도를 초과했을 때 발생할 수 있다.

주요 원인:

- 초당 요청 횟수 초과
- 분당 요청 횟수 초과
- 일일 API 사용량 초과
- 동일한 IP 또는 API Key에서 과도한 요청 발생

서버가 `Retry-After` 값을 제공한다면 지정된 시간이 지난 후 다시 요청할 수 있다.

다만 일일 사용량을 모두 소진한 경우에는 다음 사용량 초기화 시점까지 기다려야 할 수도 있다.

따라서 API를 사용할 때는 해당 서비스의 Rate Limit을 확인해야 한다.

## API Pagination의 의미

API 서버에 데이터가 매우 많다면 한 번의 요청으로 모든 데이터를 전달하지 않는다.

예를 들어 데이터가 1,000개이고 한 번에 100개씩 제공한다면 다음처럼 데이터를 나눌 수 있다.

```text
첫 번째 묶음 → 1~100
두 번째 묶음 → 101~200
세 번째 묶음 → 201~300
```

API에서는 다음과 같은 요청 형태를 사용할 수 있다.

```text
?page=2&size=100
```

이는 전체 데이터를 100개씩 나누었을 때 두 번째 데이터 묶음을 요청한다는 의미이다.

데이터를 이렇게 여러 묶음으로 나누어 전달하는 방식을 페이지네이션이라고 한다.

한 번에 전달하는 데이터의 개수는 API에서 고정할 수도 있고 `size`, `limit` 등의 값을 통해 사용자가 지정할 수도 있다.

## 화면 페이지네이션과 API 페이지네이션의 차이

API의 페이지네이션은 웹 화면에서 보이는 페이지 번호와 반드시 일치하는 것은 아니다.

웹 화면이 무한 스크롤 형태이더라도 내부에서는 다음과 같이 API를 여러 번 호출할 수 있다.

```text
첫 번째 API 요청
    ↓
데이터 100개
    ↓
스크롤
    ↓
두 번째 API 요청
    ↓
다음 데이터 100개
```

따라서 API 페이지네이션에서 `page`는 화면상의 페이지라기보다 전체 데이터 중 몇 번째 데이터 묶음을 요청하는지를 나타내는 개념에 가깝다.

페이지 번호 대신 `cursor`를 사용하는 API도 있다.

```text
지금까지 받은 데이터의 마지막 위치
    ↓
그 다음 데이터부터 추가 요청
```

이러한 방식도 넓은 의미에서 페이지네이션에 포함된다.
