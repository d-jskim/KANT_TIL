## 1. 오늘 배운 내용

오늘은 FastAPI로 데이터를 등록하고 조회하는 가장 기본적인 API 흐름을 학습했다.

```text
클라이언트가 JSON 요청 전송
→ Pydantic이 요청 검증
→ FastAPI 함수 실행
→ 데이터 저장 또는 조회
→ 정해진 응답 모델로 JSON 반환
```

메모리 저장소로 전체 흐름을 먼저 이해한 뒤, 내 프로젝트에서는 MySQL 저장 방식으로 확장했다.

## 2. Pydantic 요청·응답 모델

문서를 등록할 때 클라이언트가 보내는 형식과 서버가 반환하는 형식을 분리한다.

```python
class DocumentCreate(BaseModel):
    model_config = ConfigDict(str_strip_whitespace=True)

    title: str = Field(min_length=2, max_length=100)
    content: str = Field(min_length=10, max_length=2_000)
    source_url: str = Field(min_length=1, max_length=500)
```

`DocumentCreate`는 클라이언트가 보내는 요청 형식이다.

```python
class DocumentResponse(DocumentCreate):
    document_id: str
```

`DocumentResponse`는 `DocumentCreate`를 상속받아 다음 필드를 모두 가진다.

```text
title
content
source_url
document_id
```

`document_id`는 사용자가 입력하는 값이 아니라 서버가 생성하는 값이다.

### 배운 점

- 요청과 응답은 역할이 다르므로 별도 모델로 구분한다.
- 공통 필드는 상속을 사용해 중복 작성을 줄일 수 있다.
- `Field`로 문자열의 최소·최대 길이를 검사할 수 있다.
- `str_strip_whitespace=True`는 문자열 앞뒤 공백을 제거한다.
- 입력 검증에 실패하면 API 함수 실행 전에 `422`가 반환된다.

## 3. Python 딕셔너리를 이용한 메모리 저장소

수업에서는 Python 사전인 `DOCUMENTS`를 문서 저장소로 사용했다.

```python
DOCUMENTS: dict[str, DocumentResponse] = {}
```

`DOCUMENTS`는 변수 이름이고, 실제 자료구조는 Python의 딕셔너리인 `dict`이다.

```text
key   → document_id
value → DocumentResponse
```

예시:

```python
DOCUMENTS = {
    "doc-news-001": {
        "title": "첫 번째 소식",
        "content": "데이터를 안전하게 정제합니다.",
        "source_url": "https://example.com/news/001",
        "document_id": "doc-news-001",
    }
}
```

문서 ID를 이용하면 다음과 같이 문서를 조회할 수 있다.

```python
document = DOCUMENTS["doc-news-001"]
```

존재하지 않는 ID를 안전하게 확인하려면 `.get()`을 사용할 수 있다.

```python
document = DOCUMENTS.get("doc-news-999")
```

해당 ID가 없으면 `None`이 반환된다.

## 4. URL 중복 확인을 위한 별도 색인

문서는 `document_id`로 조회하지만, 중복 등록은 `source_url`로 확인한다.

따라서 별도의 딕셔너리를 사용한다.

```python
SOURCE_INDEX: dict[str, str] = {}
```

구조:

```text
source_url → document_id
```

예시:

```python
SOURCE_INDEX = {
    "https://example.com/news/001": "doc-news-001"
}
```

중복 검사:

```python
if request.source_url in SOURCE_INDEX:
    raise HTTPException(
        status_code=409,
        detail="이미 등록된 source_url입니다.",
    )
```

### 두 개의 딕셔너리를 사용하는 이유

```text
DOCUMENTS
document_id로 문서 전체 데이터를 조회

SOURCE_INDEX
source_url이 이미 등록됐는지 빠르게 확인
```

하나의 자료구조가 모든 조회 목적을 담당하게 하지 않고, 필요한 검색 기준에 맞는 색인을 따로 구성한 것이다.

## 5. 문서 등록 API

문서 등록 API는 `POST /documents`를 사용한다.

```python
@app.post(
    "/documents",
    response_model=DocumentResponse,
    status_code=status.HTTP_201_CREATED,
)
def create_document(request: DocumentCreate) -> DocumentResponse:
    ...
```

각 항목의 의미:

- `"/documents"`: 요청을 받을 URL
- `request: DocumentCreate`: 요청 JSON을 검사할 모델
- `response_model=DocumentResponse`: 서버 응답의 형식
- `status_code=status.HTTP_201_CREATED`: 새 문서 생성 성공 시 `201` 반환

`status.HTTP_201_CREATED`의 실제 값은 정수 `201`이다.

### ID 생성

```python
document_id = f"doc-news-{len(DOCUMENTS) + 1:03d}"
```

결과:

```text
doc-news-001
doc-news-002
doc-news-003
```

`:03d`는 정수를 세 자리로 표시하고 부족한 앞자리를 `0`으로 채운다.

이 방식은 단일 프로세스 학습에는 적합하지만, 삭제나 동시 요청이 존재하는 실제 서비스에는 적합하지 않다.

### 요청 데이터에 서버 ID 추가

```python
document = DocumentResponse(
    document_id=document_id,
    **request.model_dump(),
)
```

`request.model_dump()`는 Pydantic 객체를 Python 딕셔너리로 변환한다.

```python
{
    "title": "...",
    "content": "...",
    "source_url": "...",
}
```

`**`는 딕셔너리의 key와 value를 이름 있는 인자로 펼친다.

### 두 저장소에 데이터 기록

```python
DOCUMENTS[document_id] = document
SOURCE_INDEX[request.source_url] = document_id
```

등록이 완료되면 생성한 `document`를 반환한다.

## 6. 문서 조회 API

### 전체 목록 조회

```python
@app.get(
    "/documents",
    response_model=list[DocumentResponse],
)
def read_documents() -> list[DocumentResponse]:
    return list(DOCUMENTS.values())
```

딕셔너리의 `values()`에는 저장된 문서 데이터가 들어 있다.

문서가 하나도 없으면 `404`가 아니라 다음처럼 빈 목록을 반환한다.

```json
[]
```

목록이라는 자원은 존재하지만 내부 항목이 0개라는 뜻이므로 상태 코드는 `200`이다.

### 문서 한 건 조회

```python
@app.get(
    "/documents/{document_id}",
    response_model=DocumentResponse,
)
def read_document(document_id: str) -> DocumentResponse:
    if document_id not in DOCUMENTS:
        raise HTTPException(
            status_code=404,
            detail="문서를 찾을 수 없습니다.",
        )

    return DOCUMENTS[document_id]
```

`{document_id}`는 URL에 포함되는 Path Parameter이다.

예시:

```text
GET /documents/doc-news-001
```

## 7. HTTP 상태 코드

| 상태 코드 | 의미 | 사용 사례 |
|---|---|---|
| `200 OK` | 조회 성공 | 전체 목록 또는 한 건 조회 |
| `201 Created` | 새 자원 생성 성공 | 새 문서 등록 |
| `404 Not Found` | 요청한 자원이 없음 | 존재하지 않는 문서 ID 조회 |
| `409 Conflict` | 현재 저장 상태와 충돌 | 같은 `source_url` 재등록 |
| `422 Unprocessable Entity` | 요청 데이터 검증 실패 | 필드 누락, 길이 또는 타입 오류 |
| `500 Internal Server Error` | 서버 내부 처리 오류 | Python 코드 또는 DB 처리 오류 |

### 404와 409의 차이

```text
404
찾으려는 데이터가 없음

409
새 요청이 현재 저장된 데이터와 충돌함
```

같은 `source_url`을 다시 등록하는 요청은 JSON 형식 자체는 올바르다. 따라서 `422`가 아니라 현재 저장 상태와 충돌한다는 의미의 `409`를 반환한다.

## 8. 테스트 전에 두 딕셔너리를 비우는 이유

```python
def clear_store() -> None:
    DOCUMENTS.clear()
    SOURCE_INDEX.clear()
```

두 딕셔너리를 모두 비워야 하는 이유는 테스트 사이의 영향을 제거하기 위해서다.

`DOCUMENTS`만 비우고 `SOURCE_INDEX`를 남기면 실제 문서는 없는데 URL은 이미 등록된 것으로 판단하는 불일치가 생긴다.

```text
DOCUMENTS에는 문서가 없음
SOURCE_INDEX에는 URL이 남아 있음
→ 새 등록 요청이 잘못 409로 처리될 수 있음
```

두 저장소를 모두 초기화하면 테스트할 때마다 첫 문서 ID가 `doc-news-001`로 시작하고 같은 결과를 반복해서 확인할 수 있다.

## 9. 메모리 저장소와 MySQL의 차이

| 메모리 딕셔너리 | MySQL |
|---|---|
| 코드가 단순함 | 테이블과 관계 설계가 필요함 |
| 학습 흐름을 확인하기 쉬움 | 데이터를 영구 저장함 |
| 서버 종료 시 데이터가 사라짐 | 서버를 다시 실행해도 데이터가 유지됨 |
| 여러 프로세스가 공유하기 어려움 | 여러 요청과 서비스가 같은 데이터 사용 가능 |
| 복잡한 검색과 관계 처리에 한계가 있음 | 조건 검색, 외래 키, 인덱스 사용 가능 |

Python 딕셔너리는 데이터베이스의 일부 동작과 비슷해 보이지만, 지속성·동시성·백업·관계 관리 기능이 없으므로 운영 DB를 대체할 수 없다.

JSON 파일 저장도 단순한 내보내기에는 사용할 수 있지만, 여러 요청이 동시에 파일을 수정하는 문제와 저장 중 오류를 해결하지 못한다.

## 10. Query 요청과 Context 설계

문서를 저장하고 조회한 다음에는 저장된 문서를 근거로 질문하는 Query 구조를 학습했다.

Query 요청의 주요 필드:

```text
question
사용자가 알고 싶은 질문

context
사용자가 요청에 직접 포함한 근거 본문

document_id
서버에 저장된 문서를 찾기 위한 ID
```

`document_id` 자체가 LLM에 전달할 근거는 아니다.

```text
document_id
→ 저장소에서 문서 조회
→ 실제 content 추출
→ content를 프롬프트의 근거로 사용
```

### Context 선택 규칙

`context`와 `document_id`는 둘 중 정확히 하나만 사용한다.

```python
class QueryRequest(BaseModel):
    question: str = Field(min_length=3, max_length=300)
    document_id: str | None = None
    context: str | None = Field(
        default=None,
        min_length=1,
        max_length=2_000,
    )

    @model_validator(mode="after")
    def choose_one_context_source(self):
        has_document = self.document_id is not None
        has_context = self.context is not None

        if has_document == has_context:
            raise ValueError(
                "document_id와 context 중 하나만 입력하세요."
            )

        return self
```

다음 요청은 정상이다.

```json
{
  "question": "문서의 핵심은 무엇인가요?",
  "document_id": "doc-news-001"
}
```

다음 요청도 정상이다.

```json
{
  "question": "API는 무엇인가요?",
  "context": "API는 프로그램끼리 데이터를 주고받는 창구입니다."
}
```

두 값을 모두 보내거나 모두 보내지 않으면 검증에 실패한다.

### 프롬프트 구조

```python
def build_prompt(question: str, context: str) -> str:
    return (
        "아래 근거만 사용해 질문에 한국어로 답하세요.\n\n"
        f"[근거]\n{context}\n\n"
        f"[질문]\n{question}\n\n"
        "[답변]"
    )
```

프롬프트를 지시문, 근거, 질문으로 구분하면 사람이 읽을 때도 어떤 정보가 모델에 전달되는지 확인하기 쉽다.

### Query 응답

```python
class QueryResponse(BaseModel):
    answer: str
    sources: list[str]
```

`answer`와 `sources`를 분리하면 화면에서 답변과 근거를 별도로 표시할 수 있다.

이번 단계에서는 Query 계약과 프롬프트 생성까지 이해했고, 실제 LLM 호출은 아직 연결하지 않았다.

## 12. FastAPI 서비스 분리

현재 두 개의 FastAPI 서버를 사용한다.

```text
Profile Service
Port 8001

Match Service
Port 8002
```

구조:

```text
career_matching_service/
└─ backend/
   ├─ profile_service/
   │  ├─ main.py
   │  └─ db.py
   └─ match_service/
      └─ main.py
```

### 서비스 간 통신

```text
클라이언트
→ Match Service
```

외부 서버의 응답을 기다리는 동안 다른 요청을 처리할 수 있도록 서버 간 통신 함수를 비동기로 작성했다.

## 13. 메모리 저장소를 MySQL로 확장

메모리 딕셔너리의 데이터는 서버 종료 시 사라지므로 MySQL 연결을 시작했다.

최소 테이블:

```text
career_user
├─ user_id
└─ name

career_profile
├─ profile_id
├─ user_id
└─ profile_name

user_skill
├─ user_id
└─ skill_code
```

관계:

```text
career_user
 ├─ career_profile
 └─ user_skill ─ skill
```

### 사용자와 Career Profile의 차이

```text
career_user.name
→ 사용자 이름

career_profile.profile_name
→ 사용자가 만든 프로필의 제목
```

예시:

```text
테스트 사용자
├─ LLM 엔지니어 지원용
├─ Product Designer 지원용
└─ 특정 기업 지원용
```

### 사용자 Skill

Skill은 특정 프로필에 중복 저장하지 않고 사용자 전체 역량으로 관리한다.

```sql
PRIMARY KEY (user_id, skill_code)
```

복합 기본 키를 사용해 한 사용자에게 같은 Skill이 중복 연결되는 것을 방지했다.

기존 Skill Taxonomy의 `skill.skill_code`를 외래 키로 참조한다.

## 14. MySQL 연결

`profile_service/db.py`에서 환경변수를 이용해 DB에 연결했다.

```python
def get_db_connection():
    return mysql.connector.connect(
        host=os.getenv("DB_HOST", "127.0.0.1"),
        port=int(os.getenv("DB_PORT", "3306")),
        user=os.getenv("DB_USER"),
        password=os.getenv("DB_PASSWORD"),
        database=os.getenv(
            "DB_NAME",
            "job_skill_matching",
        ),
    )
```

배운 점:

- 비밀번호는 코드에 직접 작성하지 않는다.
- `.env` 환경변수로 DB 접속 정보를 관리한다.
- `commit()`을 실행해야 INSERT가 확정된다.
- 작업 후 Cursor와 DB 연결을 닫아야 한다.

```python
finally:
    cursor.close()
    connection.close()
```

## 15. MySQL 기반 사용자·프로필 생성

### 사용자 생성

요청:

```json
{
  "name": "테스트 사용자"
}
```

응답:

```json
{
  "name": "테스트 사용자",
  "user_id": 1
}
```

새 사용자가 생성됐으므로 상태 코드 `201 Created`를 반환했다.

### Career Profile 생성

요청:

```json
{
  "user_id": 1,
  "profile_name": "LLM 엔지니어 지원용"
}
```

처리 순서:

1. `user_id`가 실제로 존재하는지 조회
2. 사용자가 없으면 `404` 반환
3. 사용자가 있으면 `career_profile`에 저장
4. `commit()`으로 저장 확정
5. 생성된 `profile_id` 반환
6. Cursor와 DB 연결 종료

Career Profile 생성에서도 `201 Created`를 확인했다.

## 16. 오류를 해결하며 배운 내용

### DB 연결 함수 실행

잘못된 코드:

```python
connection = get_db_connection
```

이 코드는 함수 자체를 변수에 저장한다.

수정:

```python
connection = get_db_connection()
```

괄호를 붙여야 함수를 실행하고 MySQL 연결 객체를 받을 수 있다.

발생했던 오류:

```text
AttributeError: 'function' object has no attribute 'cursor'
```

### 한 항목짜리 튜플

잘못된 형태:

```python
(request.user_id)
```

올바른 형태:

```python
(request.user_id,)
```

한 개의 SQL 매개변수를 전달할 때도 쉼표를 사용해 튜플로 만들어야 한다.

### Pydantic 요청 모델과 422

`ProfileCreate`에 기존 `name`, `skills` 필드가 남아 있는 상태에서 다음 요청을 보냈다.

```json
{
  "user_id": 1,
  "profile_name": "LLM 엔지니어 지원용"
}
```

Pydantic은 필수 필드가 없다고 판단해 `422`를 반환했다.

요청 모델을 다음 두 필드로 수정해 해결했다.

```python
user_id
profile_name
```

Swagger의 Request body와 Response schema를 확인하면 현재 서버가 요구하는 데이터 형식을 확인할 수 있다.

## 18. 오늘의 핵심 정리

1. `DOCUMENTS`와 `SOURCE_INDEX`는 Python 딕셔너리이다.
2. `DOCUMENTS`는 ID로 데이터를 찾는 기본 저장소이다.
3. `SOURCE_INDEX`는 URL 중복 검사를 위한 별도 색인이다.
4. 요청 모델과 응답 모델은 역할이 다르다.
5. 새 자원 등록 성공은 `201 Created`로 표현한다.
6. 없는 ID를 조회하면 `404 Not Found`를 반환한다.
7. 같은 URL을 다시 등록하면 `409 Conflict`를 반환한다.
8. 요청 형식 검증에 실패하면 `422`가 반환된다.
9. 테스트 전에 관련 저장소를 모두 비워야 이전 실행의 영향을 받지 않는다.
10. 메모리 딕셔너리는 학습에는 편하지만 서버 종료 시 데이터가 사라진다.
11. 실제 서비스 데이터는 MySQL에 저장해야 한다.
12. `document_id`는 문서를 찾는 값이고, 실제 Context는 조회된 본문이다.
13. Query 요청은 `context`와 `document_id` 중 하나만 사용하도록 검증할 수 있다.
14. `answer`와 `sources`를 분리하면 답변 근거를 화면에서 별도로 보여줄 수 있다.
15. Git 커밋을 이용하면 메모리 방식과 DB 방식의 발전 과정을 비교할 수 있다.
