# TIL - LangChain LCEL과 Runnable

## 1. LCEL

LCEL은 LangChain Expression Language의 약자로, 여러 `Runnable`을 연결하여 실행 흐름을 만드는 방식이다.

```python
chain = prompt | model | parser
```

실행 흐름은 다음과 같다.

```text
입력
 ↓
Prompt
 ↓
Model
 ↓
Parser
 ↓
출력
```

`|`는 Python에 원래 존재하는 연산자이지만, LangChain의 `Runnable` 객체에서는 앞 단계의 출력을 다음 단계의 입력으로 연결하는 용도로 구현되어 있다.

따라서 다음과 같이 읽을 수 있다.

```text
prompt의 출력 → model의 입력
model의 출력  → parser의 입력
```

---

## 2. Runnable

`Runnable`은 LangChain에서 여러 구성요소를 같은 방식으로 실행하고 연결하기 위한 공통 규격이다.

예를 들어 다음 객체들은 Runnable 체계에서 사용할 수 있다.

```text
Prompt
Model
Parser
RunnableLambda
RunnablePassthrough
RunnableSequence
RunnableParallel
```

Runnable을 사용하는 이유는 Python으로 구현할 수 없는 기능을 사용하기 위해서가 아니다.

일반 Python에서도 함수를 선언한 뒤 `main.py` 등에서 순서대로 호출할 수 있다.

```text
함수 A 호출
 ↓
함수 B 호출
 ↓
함수 C 호출
```

LangChain은 서로 다른 구성요소를 `Runnable`이라는 공통 실행 규격으로 다루어 다음과 같은 실행 방식을 일관된 인터페이스로 사용할 수 있게 한다.

```python
chain.invoke(input_data)
chain.batch(inputs)
chain.stream(input_data)
```

따라서 작은 프로그램에서는 일반 Python 함수 호출이 더 단순할 수 있으며, 모든 처리를 반드시 Runnable로 만들 필요는 없다.

---

## 3. invoke()

`invoke()`는 하나의 입력을 하나의 Runnable에 전달하여 실행하는 기본 방식이다.

각 단계를 직접 실행할 수도 있다.

```python
prompt_value = prompt.invoke({"question": "LCEL은 무엇인가요?"})
ai_message = model.invoke(prompt_value)
raw_text = parser.invoke(ai_message)
```

LCEL로 연결하면 다음처럼 하나의 체인으로 실행할 수 있다.

```python
chain = prompt | model | parser

input_data = {
    "question": "invoke는 언제 사용하나요?"
}

result = chain.invoke(input_data)
print(result)
```

`chain.invoke(input_data)` 내부에서는 다음 과정이 순서대로 실행된다.

```text
input_data
 ↓
prompt.invoke()
 ↓
model.invoke()
 ↓
parser.invoke()
 ↓
최종 결과
```

각 단계를 연결할 때는 앞 단계의 출력 자료형을 다음 단계가 입력으로 받을 수 있는지 확인하는 것이 중요하다.

---

## 4. AIMessage와 Output Parser

`ChatOpenAI` 같은 채팅 모델을 실행하면 모델의 응답은 단순 문자열이 아니라 `AIMessage` 형태로 반환될 수 있다.

`AIMessage`는 사용자가 만든 변수명이 아니라 LangChain에서 정의한 클래스이다.

관련 메시지 클래스에는 다음과 같은 것들이 있다.

```text
HumanMessage
SystemMessage
AIMessage
ToolMessage
```

`StrOutputParser`는 모델 응답에서 애플리케이션이 사용하기 편한 문자열 형태의 결과를 얻는 데 사용한다.

Output Parser는 단순 화면 출력을 위한 것만이 아니라 LLM 결과와 이후 프로그램 로직을 연결하는 인터페이스 역할도 한다.

예를 들어 구조화된 결과가 필요하다면 JSON 등의 형태로 파싱하여 이후 DB 처리나 애플리케이션 로직에 사용할 수 있다.

---

## 5. RunnableSequence

다음 LCEL 코드는 내부적으로 순차 실행 구조인 `RunnableSequence`를 만든다.

```python
chain = prompt | model | parser
```

`print(chain)`으로 확인한 구조를 정리하면 다음과 같다.

```text
RunnableSequence

├─ first: ChatPromptTemplate
│  ├─ input_variables: ['question']
│  │
│  └─ messages
│     ├─ SystemMessagePromptTemplate
│     │  └─ template:
│     │     "당신은 어려운 AI 개념을 쉽게 설명하는 튜터입니다."
│     │
│     └─ HumanMessagePromptTemplate
│        ├─ input_variables: ['question']
│        └─ template:
│           "{question}"
│
├─ middle: ChatOpenAI
│  ├─ model_name: gpt-5.6-luna
│  ├─ reasoning_effort: none
│  ├─ use_responses_api: False
│  ├─ request_timeout: 30.0
│  ├─ max_retries: 0
│  ├─ max_tokens: 600
│  ├─ stream_usage: True
│  │
│  ├─ LangChain versions
│  │  ├─ langchain-core: 1.6.5
│  │  ├─ langchain: 1.4.3
│  │  └─ langchain-openai: 1.6.6
│  │
│  └─ OpenAI API Key
│     └─ SecretStr('**********')
│
└─ last: StrOutputParser
```

`first`, `middle`, `last`는 Runnable이 3개이기 때문에 만들어진 구분이 아니다.

예를 들어 다음과 같이 5개를 연결해도,

```text
A | B | C | D | E
```

구조는 다음과 같다.

```text
first  = A
middle = [B, C, D]
last   = E
```

따라서 `middle`은 리스트이며 필요한 경우 `chain.middle[0]`, `chain.middle[1]`처럼 접근할 수 있다.

다만 실제 애플리케이션 로직에서 내부 위치에 과도하게 의존하면 체인 순서가 변경될 때 코드가 깨질 수 있다.

---

## 6. RunnableSequence 클래스와 `|`

다음 두 방식은 같은 순차 실행 구조를 만든다.

```python
sequence_by_class = RunnableSequence(
    clean_step,
    label_step,
)

sequence_by_pipe = clean_step | label_step
```

첫 번째는 `RunnableSequence` 클래스를 직접 사용한다.

두 번째는 LCEL의 `|`를 사용하여 더 간결하게 표현한다.

```text
clean_step → label_step
```

`RunnableSequence`를 직접 import하지 않아도 `|` 양쪽의 객체가 이미 Runnable이라면 `|`를 이용해 `RunnableSequence`를 만들 수 있다.

## 7. RunnableLambda

일반 Python 함수는 그 자체로 Runnable이 아니다.

```python
def clean_text(text: str) -> str:
    return text.strip()

def add_label(text: str) -> str:
    return f"학습 주제: {text}"
```

따라서 일반 함수끼리 바로 다음과 같이 연결할 수는 없다.

```python
clean_text | add_label
```

일반 Python 함수를 LCEL의 Runnable 흐름에 포함시키려면 `RunnableLambda`로 감쌀 수 있다.

```python
clean_step = RunnableLambda(clean_text)
label_step = RunnableLambda(add_label)

sequence = clean_step | label_step
```

흐름은 다음과 같다.

```text
일반 Python 함수
 ↓
RunnableLambda
 ↓
Runnable
 ↓
| 연산자로 연결
 ↓
RunnableSequence
```

즉 `RunnableLambda`는 일반 Python 함수로는 할 수 없는 계산을 가능하게 하는 것이 아니라, 일반 함수를 Runnable 실행 체계에 참여시키는 역할을 한다.

---

## 8. RunnablePassthrough

`RunnablePassthrough()`는 입력을 변경하지 않고 그대로 출력으로 전달한다.

```text
입력
 ↓
RunnablePassthrough()
 ↓
동일한 입력
```

단독으로 사용하면 사실상 아무 작업도 하지 않기 때문에 단순한 예제에서는 필요성이 잘 보이지 않는다.

실제 의미는 Runnable 흐름 안에서 특정 입력을 그대로 보존해야 할 때 나타난다.

예를 들어 RAG에서는 하나의 질문을 검색에도 사용하면서 원래 질문도 Prompt에 전달해야 할 수 있다.

```text
                 ┌→ 원래 질문 그대로 ─────────┐
질문 ────────────┤                             ├→ Prompt
                 └→ Retriever → 검색 결과 ────┘
```

이때 `RunnablePassthrough()`는 "이 입력은 가공하지 않고 그대로 전달한다"는 역할을 Runnable 그래프 안에서 표현할 수 있다.

하지만 단순한 Python 프로그램이라면 일반 변수나 딕셔너리를 그대로 사용하는 것이 더 간단할 수 있다.

---

## 9. RunnablePassthrough.assign()

`assign()`은 기존 딕셔너리의 값을 유지하면서 Runnable 실행 중에 새로운 값을 추가할 때 사용할 수 있다.

대표적인 RAG 흐름은 다음과 같다.

```python
chain = (
    RunnablePassthrough.assign(
        context=retriever
    )
    | prompt
    | model
    | parser
)
```

입력이 다음과 같다면,

```python
{
    "question": "우리 회사의 연차 사용 규정 알려줘"
}
```

검색 후 다음과 같은 데이터가 만들어질 수 있다.

```python
{
    "question": "우리 회사의 연차 사용 규정 알려줘",
    "context": "검색된 사내 연차 규정..."
}
```

핵심은 단순히 딕셔너리에 값을 추가하는 기능이 아니다.

일반 Python에서도 다음처럼 충분히 처리할 수 있다.

```python
data["context"] = context
```

`assign()`의 의미는 Runnable 파이프라인이 실행되는 도중 기존 데이터를 유지하면서 다른 Runnable이 만든 결과를 추가하고, 그 과정 자체를 LCEL 실행 흐름에 포함시키는 데 있다.

따라서 모든 데이터 준비가 이미 일반 Python 코드에서 끝났다면 굳이 `assign()`을 사용할 필요가 없다.

---

## 10. RunnableParallel

`RunnableParallel`은 하나의 입력으로 서로 의존하지 않는 여러 Runnable을 실행하는 구조이다.

```text
              ┌→ 작업 A ─┐
입력 ─────────┤          ├→ 결과 결합
              └→ 작업 B ─┘
```

실제 장점은 특히 DB 조회, Vector Search, API 호출처럼 대기 시간이 존재하는 독립적인 작업에서 나타난다.

예를 들어:

```text
Profile DB 조회    2초
Vector Search      3초
외부 API           4초
```

순차적으로 실행하면 대략 각 작업 시간이 누적될 수 있지만, 독립적인 작업을 병렬로 처리하면 대기 시간을 겹칠 수 있다.

단, 작업 B가 작업 A의 결과를 필요로 한다면 병렬로 실행할 수 없다.

따라서 다음처럼 구분한다.

```text
RunnableSequence
→ 앞 단계의 결과가 다음 단계에 필요한 순차 작업

RunnableParallel
→ 서로 독립적으로 실행할 수 있는 작업
```

아주 짧은 문자열 처리처럼 실행 시간이 거의 없는 작업은 병렬 처리의 이점보다 관리 비용이 더 클 수도 있다.

---

## 11. stream()

`stream()`은 전체 응답이 완성될 때까지 기다렸다가 한 번에 반환하는 대신 생성되는 결과를 조각 단위로 전달한다.

```python
chunks = chain.stream(input_data)
```

이때 바로 완성된 답변이 반환되는 것이 아니라 generator 객체가 반환된다.

```text
<generator object RunnableSequence.stream at 0x...>
```

generator는 결과를 미리 모두 만들어 저장한 객체가 아니라, 값을 필요로 할 때 순차적으로 꺼낼 수 있는 객체이다.

따라서 다음과 같이 `for`문으로 결과를 하나씩 받을 수 있다.

```python
for raw_chunk in chain.stream(input_data):
    chunk = str(raw_chunk)
    print(chunk, end="", flush=True)
```

개념적으로는 다음과 같다.

```text
stream()
 ↓
generator
 ↓
chunk
 ↓
chunk
 ↓
chunk
 ↓
...
```

## 12. 토큰과 Streaming Chunk의 차이

LLM 자체는 기본적으로 이전까지의 내용을 바탕으로 다음 토큰을 순차적으로 생성한다.

```text
"철수는 학교"
 ↓
다음 토큰 생성
 ↓
"철수는 학교에"
 ↓
다음 토큰 생성
 ↓
"철수는 학교에 갔다"
```

하지만 모델이 생성하는 토큰과 애플리케이션이 `stream()`으로 전달받는 `chunk`는 같은 개념이 아니다.

```text
토큰
→ 모델이 다음 내용을 생성하는 단위

chunk
→ 스트리밍 과정에서 애플리케이션이 전달받는 결과 조각
```

따라서 다음 관계가 항상 성립하는 것은 아니다.

```text
토큰 1개 = chunk 1개
```

실제 실습에서는 다음과 같은 chunk를 확인했다.

```text
'Stream'
'은'
' 데이터를'
' 한'
'꺼'
'번'
'에'
' 기다'
'리지'
' 않고'
...
```

`한꺼번에`라는 하나의 단어도 여러 chunk로 나뉘어 전달되었다.

따라서 chunk는 한 줄, 한 단어 또는 반드시 한 토큰이라고 정의할 수 없다.

## 13. repr()로 Chunk 확인

다음처럼 `repr()`을 사용하면 chunk에 포함된 공백이나 줄바꿈을 확인하기 쉽다.

```python
for chunk in chunks:
    print(repr(chunk), type(chunk).__name__)
```

예를 들어:

```text
' 데이터를'
```

이라고 출력되면 `데이터를` 앞의 공백도 실제 조각에 포함되어 있다는 것을 알 수 있다.

실습 환경에서는 각 조각의 타입 이름이 다음과 같이 출력되었다.

```text
'Stream' TextAccessor
'은' TextAccessor
' 데이터를' TextAccessor
```

현재 확인된 사실은 `type(chunk).__name__`이 `TextAccessor`라는 것이다.

다만 클래스 이름만으로 `TextAccessor`의 정확한 구현과 역할까지 단정할 수는 없으며, 정확한 출처를 확인하려면 `type(chunk)`와 해당 클래스의 모듈 등을 추가로 확인해야 한다.

## 14. Generator는 한 번 소비하면 끝난다

다음 코드는 두 번째 반복문이 실행되지 않았다.

```python
chunks = chain.stream(input_data)

for chunk in chunks:
    print(repr(chunk), type(chunk).__name__)

for raw_chunk in chunks:
    chunk = str(raw_chunk)
    print(repr(chunk), type(chunk).__name__)
```

첫 번째 `for`문에서 generator의 값을 끝까지 모두 소비했기 때문이다.

```text
generator 생성
 ↓
첫 번째 for문
 ↓
chunk를 끝까지 하나씩 소비
 ↓
generator 소진
 ↓
두 번째 for문
 ↓
꺼낼 값 없음
```

같은 generator를 처음부터 다시 순회할 수는 없다.

스트림을 다시 생성하면 다시 반복할 수 있다.

```python
chunks = chain.stream(input_data)

for chunk in chunks:
    print(repr(chunk), type(chunk).__name__)

chunks = chain.stream(input_data)

for raw_chunk in chunks:
    chunk = str(raw_chunk)
    print(repr(chunk), type(chunk).__name__)
```

단, 이 경우 `chain.stream(input_data)`를 다시 실행하므로 모델도 다시 호출될 수 있다.

동일한 결과를 여러 번 확인하려면 먼저 리스트로 저장할 수 있다.

```python
chunks = list(chain.stream(input_data))
```

리스트는 generator와 달리 여러 번 반복할 수 있다.

## 15. batch()

`batch()`는 여러 입력을 한 번에 처리할 때 사용한다.

`dict` 하나를 직접 전달하면 문제가 발생할 수 있다.

```python
single_input = {
    "question": "batch는 무엇인가요?"
}

chain.batch(single_input)
```

`batch()`에는 입력들의 리스트를 전달해야 한다.

```python
single_input = {
    "question": "batch는 무엇인가요?"
}

results = chain.batch([single_input])
```

여러 입력을 처리한다면 다음과 같다.

```python
inputs = [
    {"question": "batch는 무엇인가요?"},
    {"question": "invoke는 무엇인가요?"},
    {"question": "stream은 무엇인가요?"}
]

results = chain.batch(inputs)
```

`dict` 하나를 넘겼을 때 발생한 `KeyError: 0`은 내부에서 첫 번째 입력을 얻기 위해 `inputs[0]`과 같은 접근을 시도했지만, 전달된 값이 리스트가 아니라 딕셔너리였기 때문에 발생했다.

정리하면 다음과 같다.

```text
invoke(input)
→ 입력 1개 처리

stream(input)
→ 입력 1개 처리
→ 결과를 여러 chunk로 순차적으로 전달

batch([input1, input2, input3])
→ 여러 입력 처리
→ 여러 결과 반환
```

## 16. RAG와 전체 Context 전달

JD와 Curriculum 같은 원문이 MySQL에 있다고 해서 반드시 Vector DB나 RAG가 필요한 것은 아니다.

### SQL 조회

정형화된 조건이나 명확한 데이터를 찾는 경우 SQL만으로 처리할 수 있다.

```text
질문
 ↓
SQL 조회
 ↓
결과
```

### 전체 Context + LLM

하나의 JD와 Curriculum 원문이 충분히 짧다면 MySQL에서 원문을 가져와 그대로 LLM에 전달할 수 있다.

```text
MySQL
 ↓
JD + Curriculum 원문
 ↓
Prompt
 ↓
LLM
 ↓
판단
```

### RAG

문서가 길어지고 실제 판단에 필요한 부분이 일부라면 먼저 관련 내용을 검색한 후 필요한 부분만 LLM에 전달할 수 있다.

```text
문서
 ↓
검색
 ↓
관련 Chunk
 ↓
Prompt
 ↓
LLM
```

RAG 필요 여부는 DB의 전체 행 개수만으로 결정되지 않는다.

예를 들어 JD가 100만 개 있어도 한 번에 짧은 JD 하나만 평가한다면 전체 100만 개를 LLM에 전달하는 것이 아니므로 RAG가 반드시 필요한 것은 아니다.

반대로 문서가 20개뿐이어도 각 문서가 수백 페이지라면 검색 과정이 필요할 수 있다.

RAG 도입 시에는 다음 과정이 추가된다.

```text
Chunking
 ↓
Indexing / Embedding
 ↓
Retrieval
 ↓
Top-k 선택
 ↓
LLM
```

검색 단계에서 중요한 정보가 누락될 수도 있으므로 RAG를 추가한다고 반드시 정확도가 올라가는 것은 아니다.

또한 RAG가 반드시 별도의 Vector DB를 요구하는 것은 아니다. SQL 검색, Full-text Search, BM25, Vector Search, Hybrid Search 등 다양한 검색 방식을 사용할 수 있다.

## 17. 오늘의 핵심 정리

오늘 배운 Runnable 계열을 "Python으로는 못 하는 기능"으로 이해하면 오히려 헷갈린다.

일반 Python만으로도 다음과 같이 구현할 수 있다.

```text
함수 선언
 ↓
main.py에서 순서대로 호출
 ↓
딕셔너리에 데이터 추가
 ↓
필요한 함수 실행
 ↓
결과 반환
```

LangChain의 핵심은 이 작업들을 반드시 Runnable로 해야 한다는 것이 아니다.

```text
일반 Python 함수 / Prompt / Model / Parser / Retriever
                         ↓
                  Runnable이라는 공통 규격
                         ↓
               LCEL로 실행 흐름을 구성
                         ↓
             invoke / batch / stream 등으로 실행
```

따라서 도구별 핵심 역할은 다음처럼 정리할 수 있다.

| 항목 | 핵심 역할 | 포인트 |
|---|---|---|
| `Runnable` | 공통 실행 규격 | LangChain 구성요소를 같은 방식으로 실행·조합 |
| `RunnableSequence` | 순차 실행 | 앞 단계 출력이 다음 단계 입력으로 전달 |
| `\|` | Sequence를 간결하게 표현 | `prompt \| model \| parser` |
| `RunnableLambda` | 일반 함수를 Runnable로 변환 | 직접 만든 Python 함수를 LCEL에 포함 |
| `RunnablePassthrough` | 입력 그대로 전달 | 원본 값을 Runnable 흐름 안에서 보존 |
| `RunnablePassthrough.assign()` | 기존 입력을 유지하며 값 추가 | 실행 중 검색 결과 등의 데이터 결합 |
| `RunnableParallel` | 독립 작업 분기 | 서로 기다릴 필요 없는 작업 실행 |
| `invoke()` | 단일 입력 실행 | 전체 결과 반환 |
| `stream()` | 단일 입력 스트리밍 | 결과를 chunk 단위로 순차 전달 |
| `batch()` | 여러 입력 실행 | 입력 리스트를 받아 여러 건 처리 |

가장 중요한 관점은 다음과 같다.

**Runnable은 일반 Python을 대체하기 위한 것이 아니라, LLM 애플리케이션의 여러 구성요소를 같은 실행 규격으로 조합하기 위한 LangChain의 추상화이다.**

따라서 단순한 프로그램이라면 일반 Python 코드가 더 적합할 수도 있고, Runnable 기반 실행 구조가 필요한 경우에 선택해서 사용하는 것이 중요하다.
